# 平台后端：账号、联机房间、钱包、排行、额度与熔断

> 适用于平台上所有需要后端的游戏。2026-10-19 按代码现状整理：平台 0.25、`arcade-kit` 0.21（`packages/arcade-kit`）、自托管 `packages/arcade-host`。
> 数字（限额、预算、阈值）以代码为准：平台在 `platform/worker/api/config.ts`，房间在 `packages/arcade-kit/src/room.ts` 和 `meter.ts`；本文和代码不一致时改本文。
> 依据：Cloudflare 官方文档（抓取于 2026-10-13/14/15）和一次实测（第 2 节）。标"推断"的是没有实测的判断。
> 其他文档引用本文的节号（如 4.6、5.3、5.9、6.6、7.2、15.x），改动时保持节号不变。

## 0. 摘要

- 全部用 Cloudflare：静态页和接口用 Workers，联机房间用 Durable Objects（下称 DO），账号和成绩等数据用 D1。也可以自托管（3.1）。
- 房间必须用休眠写法。实测 4 个真人打 30 分钟，计费时长约 1.35 GB-s，普通写法约 230 GB-s；费用主要来自请求次数和存储写入行数，时长不重要。
  所以第 4 节的写入规则是硬规则。
- 现在跑在 Workers 免费版：额度是全账户共享的、按天重置，超了操作直接失败（不是多收钱）。额度防护有三层（第 6 节）：房间硬限制（4.6）、
  每个游戏 Worker 的房间计量（kit `RoomMeter`，4.7）、平台接口自己的计量与分级停服（6.6）。按账单金额熔断、GraphQL 对账、墓碑版本没有做（6.2、6.4）。
- 不是每个游戏都要实时联机：掼蛋、德州、麻将、飞驰有好友房；开盘不做同场，做每日挑战排行（9.2）。
- 账号用用户名 + 密码，建号时给一个恢复码。当前是**邀请制**：新人凭老用户的邀请码注册，公开注册由管理员开关（5.8、15.20）；游戏要登录才能进（15.8）。
  账号系统的第一目标是防刷、守住额度：匿名只开放注册、登录、找回、`GET /api/me`，写操作一律要登录，账号、IP、全站三级日上限（5.4）。
- **排行榜不防作弊**（能作弊算玩家自己的本事）：游戏页直接调 `POST /api/scores` 交分，平台只防刷额度、查数据合法性（9.2、15.5）。
- **钱包**（筹码，5.9；方案正本 `docs/economy.md`）：一人一行，带入、结回、放弃只有游戏服务端经服务绑定 RPC 能调，浏览器只能看和领补给。
- 所有代码在单一总仓库 `yyyu-star/arcade`；每个模块可以随时拆出去单独部署（AGENTS.md 第 1、2 节）。

## 1. 约束

| 约束 | 落实 |
|---|---|

## 2. 实测结果（2026-10-13，临时实验 Worker，经香港出口；该 Worker 已删）

同一套游戏逻辑分别用休眠写法（H）和普通写法（N），模拟真人每回合思考 3–12 秒、每 25 秒一次心跳，跑 7 分钟，按 30 分钟线性推算：

| 每桌 30 分钟（推算） | H，4 真人 | H，1 真人 + 3 AI（AI 每步一个闹钟） | N，4 真人 |
|---|---|---|---|
| 计费时长 GB-s | ≈1.35 | ≈4.2 | ≈230 |
| 调用次数（最保守，1:1 计） | ≈232 | ≈671 | ≈516 |
| 存储写入行数 | ≈250（每步约 1.1 行） | ≈680 | ≈250 |
| 出一步到收到广播的往返时间 | p50 93 ms / p99 241 ms | 未单独测 | p99 425 ms |

- 休眠期间不计时长；挂着 30 秒的回合闹钟不影响休眠；`setWebSocketAutoResponse` 的心跳不出现在任何计量里。
- AI 用闹钟逐步驱动会让请求数涨到真人桌的约 3 倍，所以 4.4 改成批量出牌。
- 部署 4 次（各观察约 100 秒）没有断开 WebSocket，休眠房间 13–64 秒内换上新代码；但官方文档说部署会断连，设计上按"会断"处理（4.5）。
- GraphQL 分析数据延迟 1–13 分钟、会丢分钟行、数值来回跳、会拿到缓存旧值，所以只能用来对账，不能做实时熔断依据。
- 休眠写法下入站消息在调用类型 `hibernation` 里，官方价格页按 20:1 折算；本文按 1:1 估算，作最坏情况。
- 其余实验（E1 路径路由与 WebSocket、E4 断线续局、E5 开盘重放 CPU）的结论见第 11 节。

## 3. 总体结构

```
浏览器（同一个站点主机名 <站点>）
 ├─ /                         → arcade Worker：平台界面（静态）
 ├─ /api/*                    → arcade Worker：账号、云存档、好友、排行榜、钱包、社交、管理、熔断状态
 │                               绑定：D1（`DB`，库名 arcade）；Cron 每天一次清理（7.3）
 │                               服务绑定入口：默认入口（fetch 认人 + blockedAmong）、WalletService（钱包 RPC）
 └─ /games/<id>/*             → 游戏自己的 Worker（路径路由，不经过平台）
      ├─ 静态资源（免费，不计请求）
      ├─ 首页三个路径 → 登录闸门（经服务绑定 ARCADE 问 /api/me，15.8）
      ├─ 房间/匹配入口（kit 的 acceptCreate / acceptJoin / acceptMatch）→ Room DO、RoomMeter DO、Queue DO（休眠写法，SQLite 存储）
      └─ 服务绑定 → arcade Worker（ARCADE：认人；WALLET：钱包，带 props.game）
```

- **依赖方向只有一个**：游戏依赖平台，平台不依赖任何游戏。发布顺序固定为 D1 迁移 → 平台 → 游戏。平台的 RPC 接口只增不改。
- **平台独占 D1**：表结构和迁移只在 `platform/` 里改。游戏通过同域 `/api/*` 或服务绑定访问平台（AGENTS.md 第 1 节第 4 条）。服务绑定不另收请求费，但调用 DO 的每个 RPC 方法都算一次 DO 请求。
- **路径设置**：游戏 Worker 的静态资源配置用 `run_worker_first` 列出要先进 Worker 的路径（首页三个路径、房间和接口路径），防止单页应用回退规则吞掉它们。
- **平台入口只认站点主机名**：平台 `workers_dev: false`、`preview_urls: false`（版本预览地址会绕过网关限速，还会连正式 D1），`/api` 先看 Host，只接受 `SITE_ORIGIN` 的主机名，别的一律 404。
- **本地开发**：平台接口的本地服务是 `npm run dev:api`（`wrangler dev`，端口 5181；5180 是平台界面的 vite，不带接口）。**起之前要先 `npm run build`** 生成 `dist/`
  （`assets.directory` 指向它，没有时 wrangler 起不来）。游戏本地联调时，开发服务器把 `/api` 代理到 5181。

### 3.1 部署形态

同一份代码有两种部署，模块代码和 `wrangler.jsonc` 都不用改：

- **Cloudflare（正式环境）**：平台 1 个 Worker + 每个游戏 1 个 Worker。只由 main 上经 PR 合并的提交触发；test 作业跑测试并打包（不拿凭证），deploy 作业经维护者在 `production` 环境批准后，
  用 `tools/deployer/` 里钉死的 wrangler 部署（平台先 `wrangler d1 migrations apply` 再发布）。站点主机名和 D1 的库 id 是 `production` 环境的 secret，运行时 Secret 用 `wrangler secret put` 设，都不进仓库（第 8 节）。
- **自托管（`tools/selfhost`，详见 `tools/selfhost/README.md` 和 `packages/arcade-host/README.md`）**：一个 workerd 进程跑平台和所有游戏，`arcade-host` 补上 D1、静态资源、路由和 Cron，打成发布包（二进制 + systemd，或 Docker）。
  平台库在 **SQLite 和 PostgreSQL 里二选一**（部署时定，不能共存）：SQLite 时房间落在数据目录；PG 模式（`--db pg`）下房间默认仍落盘，加 `--storage memory` 后房间也进 PG
  （kit 0.21 起的 `KIT_STORE` 可插拔存储，每步改动一个事务写进 PG，重启后按存着的闹钟叫醒房间），此时所有有 DO 的游戏的 kit 都要 ≥ 0.21，不够 `build.mjs` 直接报错。
  自托管没有 Cloudflare 的额度，4.7 和 6.6 的额度门槛只是默认值，可按机器能力调；Secret 从环境变量取（pepper 用上之后不能丢，要和备份分开另存）。

## 4. 实时房间规范（arcade-kit/room，所有游戏必须遵守）

这些规矩由 `packages/arcade-kit` 的 `GameRoom` 基类实现，每条都有测试和反证（把代码改坏、确认测试会失败）；游戏只写规则（`RoomGame`），不自己写房间。
联机房间统一基于 kit：房间类继承 `GameRoom`，游戏 Worker 的路由只接 `acceptCreate` / `acceptJoin`（匹配用 `acceptMatch`），浏览器用 `RoomClient`；用法见 `packages/arcade-kit/README.md`。

### 4.1 写法

- 只用 `ctx.acceptWebSocket`，禁止 `ws.accept()`。（游戏 Worker 里拒绝进房时要先接受升级再关，那是普通 Worker 的 `server.accept()`，不在房间里，见 4.5。）
- 计时器只用一个闹钟，禁止 `setTimeout` 和 `setInterval`：
  - 到期时间不另存表：房间寿命、没人多久关房、这一手 30 秒、掉线宽限 60 秒、电脑没算完，每次都从状态那一行算出最早的那个；
  - **闹钟只往早挪**：最早时间比现在设的更早才 `setAlarm`（它也算一行写入）。期限往后推时不动，到点醒来发现没到期再改；
  - 闹钟时间以 `getAlarm()` 读到的为准（每个实例第一次进入口时读一次，之后内存里同步更新）；
  - 写完状态后广播出错，算好的闹钟照样设上；闹钟里游戏代码出错，不往外抛，60 秒后再醒来重试（重试的 `setAlarm` 也计入写入）。
- 心跳用 `setWebSocketAutoResponse("ping","pong")`，不唤醒房间，也不计费。
- 每个连接的 attachment 里只放 `{userId, 昵称}`（座位从状态里按 userId 查）。内存里的东西一律当缓存，被驱逐后从存储重建（测试用 `evictDurableObject` 真的驱逐过）。
- **构造函数和读路径不碰存储**：只在开房时建表，读之前先查表在不在。探一个不存在的房间码写 0 行、不建表。
- **房间只认 kit 拼的内部请求**：房间的 `fetch` 只接受内部主机名的 `/ws`，游戏 Worker 把浏览器的原始请求转进来会被 400 拒掉，浏览器自带的身份头不会被当真；开房走 DO RPC，身份是参数。
  这些内部地址不在包的 `exports` 里，游戏只能用 `acceptCreate` / `acceptJoin`（5.3）。
- 存储用 SQLite 后端，迁移用 `new_sqlite_classes`（**免费版只支持这一种**，4.7）。
- 写存储不必 `await`，但**省不掉存储等待**：DO 的输出闸门会等写入确认后才把广播发出去，出牌往返比心跳多约 40 ms，这是正确行为。
- 创建房间时设 `locationHint: "apac"`（只是尽量就近）。房间关闭时调用 `deleteAlarm()` 和 `deleteAll()`，不留下存储。
- PG 模式（`KIT_STORE`，3.1）下 kit 用内存镜像：读写仍是同步的，"一步之内没有 `await`"的规矩不变，这一步的脏行在广播之前一次事务提交，提交成功才把这一步的 send/close 发出，语义等同输出闸门。

### 4.2 写入预算（费用关键）

- **每步最多写 2 行**：状态一行，外加需要时的 `setAlarm`。计数器、到期时间和序号都合进状态那一行，不另起行。
- **不记回放**：现在没有任何地方读它，关房时还会随 `deleteAll()` 删掉。种子只在开局时用一次，不存。
- **状态没变不写**：没入座的人进出、在线时又从别的设备连进来，都是 0 行、不广播。
- **实测**（`packages/arcade-kit/test/room.test.ts`，每条都断言）：

  | 操作 | 写入行数 |
  |---|---|
  | 开房 | 4：建表 2（SQLite 记建表也算写入，一个房间只这一次）+ 状态 1 + 闹钟 1 |
  | 房主第一次连上、掉线后回来 | 1 |
  | 没入座的人进出、在线时换设备 | 0 |
  | 出牌（含电脑跟着批量出） | 1；最早期限变早时 2 |
  | 到点醒来但还没到期 | 1（只改闹钟） |
  | 超时代出、转托管 | ≤ 2 |
  | 探一个不存在的房间码 | 0 |
  | 关房 | 1（`deleteAlarm` + `deleteAll`） |

- **少建索引**：每更新一个索引也要多算一行。kit 在测试里断言"每步写入行数 ≤ 2"（开房那一步另算），超了测试就失败。

### 4.3 状态、协议与隐藏信息

- **服务端说了算**：牌堆、手牌、出牌合不合法都在房间里算。每个玩家只收到自己能看到的信息，**绝不下发别人的隐藏信息**（别人的手牌、种子）。种子只在服务端生成。
- **消息顺序**：每一步先写存储（不 await），再广播。每条消息带 `seq`，客户端发送时带 `moveId`，服务端据此去重。
- **`baseSeq`（必填）**：上行的 `act` 带做决定时看到的最新 `seq`。房间记下牌局最后一次变化（开局、出了一步）时的 `seq`，`baseSeq` 比它小就回 `stale`、不做，
  免得断线前点的旧操作在重连后被套到新的一手上；没带回 `bad_message`。`RoomClient` 自动带上，重发时带原来的值。
- **错误码不能带隐藏信息**：游戏 `apply` 返回的 `{ error }` 会原样发给出手的人，只能是固定短码；房间把不符合 `^[a-z][a-z0-9_]{0,31}$` 的换成 `illegal_move`。
- **快照体积**：重连一律发全量快照（4.5）。`arcade-kit/game` 的 `snapshotBytes(rules, state)` 算出所有座位里最大的那份，游戏在规则测试里挑最大的局面断言上限。
- **版本兼容**：协议带版本号 `v`，状态带结构版本号。新旧代码可能并存几十秒到 20 分钟，消息格式只增字段、不改含义；服务端可下发 `minClientVersion` 强制太旧的页面刷新；
  改规则只对新开的牌局生效，进行中的牌局按状态里记的规则版本打完。
- **规则核心**：纯函数，浏览器和房间共用。

### 4.4 AI 与单机

- **单机对 AI 完全在浏览器里跑**，不连服务器，不占任何额度。
- **联机桌里 AI 补位**：不是每步一个闹钟。轮到 AI 时，一次把它到下一个真人回合之间的所有步算完，一次性广播，每步带相对延迟，客户端按延迟播放动画
  （`maxAiBatch` 限制一次连算几步，剩下的按闹钟接着算）。提前透露的只有 AI 已经出了的牌，本来就是公开信息。真人在一批 AI 步中途接管座位时，以服务端状态为准。
- 闹钟失败会自动重试最多 6 次、每次都计费，所以 AI 代码出错必须吞掉异常并记录，不能让闹钟反复重试。
- Worker CPU：`limits.cpu_ms` 在免费版设不了（错误码 100328），没设；掼蛋 hard 档单次决策 p99 0.66 ms（开发机实测）。

### 4.5 断线、后台与部署

- **客户端（`arcade-kit/client`）**：
  - 断线后按指数退避加随机抖动重连（0.5 秒起，封顶 15 秒，乘 0.5–1 的随机系数）。重连一律回全量快照（`welcome`），不补发缺的事件，客户端整桌重画；没收到确认的出牌按原来的 `moveId` 和 `baseSeq` 重发。
  - 页面从后台切回来（`visibilitychange`、`pageshow`）时立即检查连接（iOS Safari 和微信切后台会挂起连接）。
  - 收到 1008、1009 或 4000 段的关闭码时**不重连**；1013 照常按退避重连。
  - 连着 20 次没进得了房间（没收到 `welcome`）就停下，提示"连不上"让用户点重试。退避和失败次数在收到 `welcome` 时才清零，不在 `onopen`（被拒的连接也会先 open 再关）。
  - 进房被拒时游戏 Worker 不回 HTTP 4xx（浏览器的 WebSocket 拿不到状态码），而是先接受升级、马上用关闭码关掉。

  **关闭码**（`arcade-kit/protocol` 的 `CLOSE`）：

  | 码 | 意思 | 客户端 |
  |---|---|---|
  | 1008 | 发太快（令牌桶）或其他违规 | 不重连 |
  | 1009 | 单条消息超过 4 KB | 不重连 |
  | 1013 | 平台暂时认不了人（`/api/me` 不可用、超时），仍然拒绝进房（fail-closed）；进房猜码超限也是它 | 按退避重连 |
  | 4000 | 房间关了（寿命到、没人、入站额度用完、`quota` 收场） | 不重连 |
  | 4001 | 同一个账号在别处连上了，这条让位 | 不重连 |
  | 4003 | 没入座的连接满了 | 不重连 |
  | 4004 | 没有这个房间 | 不重连 |
  | 4005 | 页面太旧，或版本号不是数字 | 不重连，提示刷新 |
  | 4029 | 这个人的重连次数用完 | 不重连 |
  | 4030 | 这个人的入站消息超过他那一份 | 不重连 |
  | 4401 | 没登录 | 不重连，提示去登录 |
  | 4403 | 不是本站页面发起的（`Origin` 不对或没带） | 不重连 |
  | 4503 | 今天联机额度快用完了，不进新人（坐过的人照常回来） | 不重连 |
- **几个时间要互相配合**：
  - 回合计时 30 秒：掉线玩家轮到时，服务端按"最小合法出牌"代出，不判负。**重连不重置这一手的 30 秒**（不然隔 29 秒重连一次就能一直拖着），只有托管被收回、又正好轮到他时才从头算。
  - 掉线宽限 60 秒：之后转为 AI 托管，玩家回来可以收回。宽限只在开打以后才计时。
  - 房间内**没有入座的真人连着**超过 10 分钟才关闭。只连着没入座的人（旁观）也算"没人"。
- **续局的写法**（实验 E4 踩过的坑，kit 必须照做，并有"断线瞬间正在出牌"的测试）：只向**已入座**的连接广播；"算补发、发快照、标记入座"放在一段**没有 `await`** 的代码里；广播放在 `await`（如设闹钟）**之前**。
- **发布**：部署时正在打的房间不断线，但会一直跑旧代码，空闲约 1 分钟后才换新，所以**协议必须新旧兼容**：新版本先能理解旧消息，再上线用新消息的客户端。
  要强制换代码：断开连接后调 `ctx.abort()` 重置房间（能用但不保证每次成功）。避开晚上高峰发布。

### 4.6 硬限制（防 bug 失控，也防刷）

| 项 | 默认值 |
|---|---|
| 单条**入站**消息 | 4 KB，超了断开（1009）。出站快照另有体积预算，游戏用 `snapshotBytes` 自己断言（4.3） |
| 每个连接的发送频率 | 令牌桶：每秒 5 条，最多攒 10 条；超了断开（1008），客户端不重连 |
| 每个房间一生的入站消息 | 3,000 条（游戏可调：掼蛋 8,000，德州、麻将 4,000），**含会写库的重连**，超了房间结束（4000）；日志记下发得最多的 userId 和条数（不记内容） |
| 每个人能用掉的入站 | 房间一生额度的四成（`maxInboundShare` 0.4），超了只断开这个人（4030），他以后也进不来，房间照常 |
| 每个人的重连 | 一生 300 次"掉线后回来"（只数会写库的那种），超了 4029。按 userId 记：离座再坐下也不清零 |
| 没入座的连接 | 最多 4 个账号，超了 4003。入座的人、房主、开打后绑过座位的人不占这个数 |
| 房间最长寿命 | 3 小时（游戏可调：掼蛋 8 小时，德州 6 小时，麻将 4 小时） |
| 没有入座的真人连着 | 10 分钟后关闭 |
| 每个用户同时开着的房间、每天开房数 | `roomsPerUser`、`dailyRoomsPerUser`，由 `RoomMeter` 管（4.7）；kit 默认 1 个 / 每天 6 个，各游戏在 `KIT_QUOTA` 里调 |
| 电脑一次连续出手 | 64 步（游戏可调：掼蛋 3 步） |
| 开房 | `acceptCreate`：要登录、查 `Origin`，先过 `RoomMeter` 的按人和全站名额；没有人机验证。失败回 JSON `{error}`：`login`、`forbidden`、`has_room`（带已开房的码）、`daily_limit`、`busy`、`unavailable`、`bad_options` |
| 进房猜码 | 房间码只有 6 位：按人、按 IP 数"码不存在"（`joinMissesPerUser` 20 / `joinMissesPerIp` 60，每小时）；超了进任何房间都回 1013，自己人照常进，说不出房间在不在 |
| 匹配桌（kit 0.20.0，设计 `packages/arcade-kit/docs/match.md`） | 每个游戏一个排队 DO（`Queue`，每档一个实例，0 行存储、一个闹钟），最多等 15 秒，凑满或到点 ≥ 2 个真人就经内部 RPC `kitCreateMatch` 开一个普通房间（预定座位，20 秒没来的换电脑并退回他的开房名额），只剩自己就转单机；每人每小时入队 ≤ 30 次，每档队长 ≤ 200；找平台屏蔽名单、建房各最多等 3 秒，超时整桌转单机。匹配桌只许被排进来的人入座，没有房主、不显示房间码、不能旁观；开房名额、计量和好友房共用 |
| Worker CPU | `limits.cpu_ms` 免费版设不了（4.4），没设 |

kit 把每个入口都包一层：fetch、RPC、webSocketMessage、alarm、close。包装层先计数、再查限制、最后才进游戏代码，所以异常和重试也会被计数。

**已接受的残余风险**：
- **入站额度被刷光、整桌提前结束**：一个人最多用四成，要把整个房间的额度用完得 3 个账号一起刷；写入被房间的总额度封住，**刷不爆额度**，最坏是一桌人提前散场。
- **多个账号各开房间，刷光全账户当天的 DO 写额度**：DO 写行是全账户每天 10 万行（4.7），房间之间不共享。每人开房名额和各游戏的 `stopWrites` 已把单个游戏封在自己的份额内，
  但一个游戏的份额仍可能被几个号占满，那一天该游戏的好友房失败；平台的 D1 和账号不受影响。邀请制下接受；公开注册开着时要有人盯。
- **每次进房都问平台一次 `/api/me`**（含被房间拒掉的）：房间的额度和连接上限管住了写库和广播，管不住这次调用，要靠平台自己的限流（15.6）。

### 4.7 免费版 Durable Objects 额度（2026-10-14 查官方文档）

Workers 免费版**只能用 SQLite 后端的 DO**，迁移必须写 `new_sqlite_classes`，否则部署报 `free_tier_requires_sqlite`。额度按天算、UTC 0 点重置，**超了操作直接失败**：

| 项 | 每天 |
|---|---|
| 请求（HTTP、RPC、WebSocket 消息、闹钟都算） | 100,000 |
| 时长 | 13,000 GB-s |
| 读行 | 5,000,000 |
| 写行（`setAlarm` 也算 1 行；`deleteAll` 删掉的行也算写） | 100,000 |
| 存储 | 共 5 GB |

"收到的 WebSocket 消息按 20 条算 1 次请求"官方原文只列在付费版一栏，本文对免费版按 1 条算 1 次（保守）。写行最紧：一局掼蛋几百步、每步 1 行，粗算每天够打一两百局。

**房间计量 `RoomMeter`**（kit `arcade-kit/meter`，每个游戏 Worker 一个全局实例，游戏导出、绑成 `METER`）：房间数自己写了几行，攒够 `meterBatch`（200）行报一次；开房先向它占名额。门槛在游戏 `wrangler.jsonc` 的 `vars.KIT_QUOTA` 里改：

| 门槛 | 默认 | 到了以后 |
|---|---|---|
| `roomsPerUser` / `dailyRoomsPerUser` | 1 / 6 | 开房回 409 `has_room` / 429 `daily_limit` |
| `dailyRooms` | 300 | 全站今天不再开房，503 `busy` |
| `busyWrites` | 60,000 | 不开新房、不进新人（4503），在打的照常 |

## 5. 账号、云存档、好友与房间登记

### 5.1 账号与登录

**用户名 + 密码**，注册时同时给一个**恢复码**，忘了密码靠它找回。不做游客自动建号；不收手机号、邮箱等身份信息。当前是邀请制（5.8、15.20）。
更多登录方式（邮箱验证码、passkey、第三方登录）没有做，也没有排期：要做时先实测国内可用性。实现方式是自己写会话表和凭证表，不引入认证框架。

**注册**（`POST /api/auth/register`；管理员建号的校验和下面完全一样）：
- **用户名**：只用来登录，不展示给别人。NFKC 归一化、转小写，要求 `^[a-z0-9_]{3,20}$`，所以大小写不敏感地唯一。保留 `admin`、`root`、`system`、`arcade`、`official` 和各游戏 id 等。
- **密码**：NFKC 归一化（NIST SP 800-63B 的做法），不去空格、不改大小写。长度按码点数算 8–128 个；拒绝一小份最常见的弱密码表（约 1,000 条）和与用户名相同的密码。
- **昵称**：展示用，2–12 个字，可以用中文。NFKC、去首尾空白、连续空白合成一个，不许控制字符和零宽字符；过一份敏感词表。
  **保留电脑人物名**（`docs/project.md` 第 3 节）：繁体折成简体、转小写、去掉空白标点数字拉丁字母后，和保留名整名相等的都拒绝（'老张a'、'老張'、'老 张' 拦，'小美丽' 这类只是包含的照常可用）；含"电脑""官方""管理员""系统"的也拒绝。
  名单在平台里单独存一份（`validate.ts` 的 `RESERVED_PERSONAS`，按游戏 id 分组，测试保证和 `games.ts` 登记的游戏一一对应），不引用游戏代码；游戏加、改电脑人物时在它的 PR 说明里写上名字，再开一个平台 PR 补进那一组。
  不读游戏公开的 JSON：这是注册时服务端的检查，跨 Worker 取文件，游戏没部署或超时时检查会悄悄失效。
- 注册成功就登录（发会话 cookie），并显示**恢复码**一次：20 位 Crockford base32（约 100 bit），每 5 位一组，可复制、可存图。服务端只存它的 HMAC，丢了只能登录后换新的。
- 用户名已被占用返回 409，等于告诉别人"这个用户名存在"。接受：用户名不对外展示，知道它存在也还要猜密码，而猜密码有 5.4 的限流。登录时用户名不存在也白算一次哈希（`burnPasswordHash`）拉平耗时，看不出用户名在不在。

**密码哈希**：
- WebCrypto PBKDF2-SHA256，每个用户 16 字节随机盐，迭代 100,000 次（`vars.LIMITS.pbkdf2Iterations`）；结果再用 pepper（Secret `PEPPER_PW`）做一层 HMAC-SHA256，这样数据库被拖走而 Secret 没泄露时离线猜密码无从下手。
- 存成 `pbkdf2-sha256$<迭代次数>$<pepper kid>$<盐>$<哈希>`。迭代次数或 pepper 变了，用户登录成功时透明地重新哈希（多写 1 行），不用迁移。
- **免费版 CPU 上限 10 ms，10 万次迭代的 PBKDF2 压在这条线上**：线上登录一次 CPU p99 约 39–55 ms、p50 约 2.7 ms，0 错误（2026-10-14/15 实测）；文档说 isolate 允许"偶尔"超过 10 ms、"持续"超才被终止（1102）。
  只发生在注册、登录、找回、再验证这几个低频接口。**决定**：参数不改，维护者定期看 Cloudflare 统计里 arcade 的 errors 和 1102；持续出现（连着几天，或一天里成批）就开 PR 把 `pbkdf2Iterations` 设成 50000（本地约 8 ms），老哈希登录时自动升级。
  开付费版（CPU 上限 30 秒）后再透明重哈希回 10 万。这是现在开付费版的唯一理由（第 14 节）。

**恢复码、会话令牌、IP**：都只存 HMAC-SHA256，各用各的 pepper（Secret `PEPPER_RC`、`PEPPER_SID`、`PEPPER_IP`）。
- Secret 的值写成 `<kid>:<随机串>`，库里每个哈希都记着 kid。换 pepper 时把旧值放进对应的 `*_PREV`，按 kid 选用：密码在下次登录成功时换新；会话令牌的 `PEPPER_SID_PREV` 至少保留 400 天（会话最长寿命）；
  恢复码的 `PEPPER_RC_PREV` 要保留到库里没有旧 kid 的恢复码为止；只有一个 `*_PREV` 位置，旧 kid 没清完不能再换第二次；IP 不需要 `PREV`（换了只是限流计数从零开始）。
- 恢复码（100 bit）和会话令牌（256 bit）本身是高熵随机数，pepper 只是多一层，平时不轮换；真怀疑会话被盗时直接删掉全部会话比换 pepper 快。
- 所有哈希比对都用常量时间比较。恢复码存 HMAC(用户 id + 归一化后的码)；输入时不分大小写、忽略横线和空格，`I`/`L` 当 `1`，`O` 当 `0`。
- 会话令牌：32 字节随机，cookie 里是 `<kid>.<令牌>`，库里存它的 HMAC。IP：取 `CF-Connecting-IP`，IPv6 只取前 /64，HMAC 后截断，只拿来当限流计数的键，不存原文。

**忘记密码**（`POST /api/auth/recover`）：用户名 + 恢复码 + 新密码 → 设新密码、生成新恢复码（显示一次）、注销这个账号的所有会话，再给当前设备发新会话；成功后清零登录失败计数。
找回本身不按用户名记失败、也不锁，只靠 `rec:ip` 和全站每小时上限：恢复码约 100 bit，靠猜不现实；而按用户名锁的话，别人知道用户名就能同时锁住登录和找回。

**会话**：
- cookie `__Host-sid`：HttpOnly、Secure、SameSite=Lax、Path=/、不设 Domain，有效 400 天。`__Host-` 前缀保证同注册域名下的其他子站读不到、也覆盖不了它。离上次续期超过 30 天的请求顺手续期（多写 1 行）。
- 另设一个非 HttpOnly 的提示 cookie `__Host-arcade_li=1`（同样 400 天）。平台页和游戏里的脚本看到它才调接口，没登录的玩家在页面上一个 `/api` 请求都不发；例外是游戏登录闸门（15.8），每次打开游戏首页都问一次 `/api/me`。会话失效时服务端把两个 cookie 一起清掉。
- `last_seen_at` 每小时最多更新一次（1 行），用于好友页的"N 天前来过"和 1 年清理。本地开发：浏览器对 `http://localhost` 也接受 Secure cookie；自动测试里用 `https://` 地址。

**改密码、换恢复码、退出其他设备、注销账号**：界面只放在平台页，要再输一次当前密码（注销也可以用恢复码），见 5.2。改密码后注销其他所有会话，当前设备换新令牌。

**不活跃清理**：1 年没登录（`last_seen_at` 早于 365 天前）的账号，由每天的 Cron 按注销的流程删除，连同云存档和好友关系；每次最多删 200 个。**管理员账号不清**。隐私说明里写明。

### 5.2 同域的安全边界

所有游戏和平台在同一个域名下，任何一个游戏有 XSS 漏洞，都能借用户的 cookie 调 `/api`（HttpOnly 防不住同域 fetch），服务端也分不清请求来自平台页还是游戏页。所以：

- **CSRF**：所有写请求（POST、PUT、PATCH、DELETE）必须带 `X-Arcade: 1`，并且 `Origin` 等于配置的站点地址（变量 `SITE_ORIGIN`，部署时由 `SITE_HOST` 注入），否则 403。不开 CORS。
  只靠 SameSite=Lax 不够：它按"站点"算，同注册域名下的其他子站和我们同站。这些检查**只挡浏览器**：脚本可以随意伪造，作用是防 CSRF 和便宜地拒掉；防脚本刷量靠 5.4 和 6.6。
  唯一的例外是 `/api/admin/*` 带 `Authorization: Bearer` 头的请求（命令行建号工具）：浏览器跨站发这个头要先预检，而我们不答应预检，所以跨站网页发不出去；Bearer 只对 `/api/admin/*` 有效（5.8）。
- **GET 不改业务数据**（账号、存档、好友关系）。它可能顺带写一些记录（`last_seen_at`、会话续期、限流计数），被别的站点诱发也没有危害。
- **敏感操作必须重新验证**：改密码、换恢复码、退出其他设备、注销账号，请求体里要带当前密码（注销也可以带恢复码）。再验证失败单独计数（`reauth:fail:<userId>`，规则同登录失败），
  既挡住拿到 cookie 的人借这些接口猜密码，又不和登录失败共用一把锁。
- **游戏页能调的接口**（只凭 cookie）：`GET /api/me`、云存档读写、`GET /api/friends`、交分和读榜、上报位置、邀请的发收、好友动态和挑战等（15.x 标"游戏页"的）。其余接口的界面只放在平台页。
  这是**界面约定**，服务端拦不住，真正的防线是再验证和 CSP。存档读写和交分可以带"预期账号" `userId`，和会话不一致时回 409 `wrong_user`（15.3、15.5）。
- **游戏 Worker 不碰会话令牌**：登录闸门和联机进房只把浏览器的整串 Cookie 原样转给 `/api/me`，自己不解析、不保存，只拿回 userId 和昵称。
- **CSP**：平台用 `platform/public/_headers` 给页面加内容安全策略，`platform/test/headers.test.ts` 逐条锁住：
  ```
  Content-Security-Policy: default-src 'self'; script-src 'self' https://static.cloudflareinsights.com; style-src 'self';
    img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none';
    form-action 'self'; object-src 'none'
  X-Content-Type-Options: nosniff
  Referrer-Policy: same-origin
  ```
  - 唯一的外站来源是 Cloudflare Web Analytics 的脚本（站点所在 zone 自动注入）；上报走同源 `POST /cdn-cgi/rum`，`connect-src` 不放外站。
  - 界面和构建产物都没有内联脚本和内联 style，所以 `style-src` 不放 `'unsafe-inline'`，以后也不要为了省事加；`img-src` 放 `data: blob:` 是因为恢复码"存成图片"在浏览器里用 canvas 现画。
  - `_headers` 只作用于静态资源，`/api` 的响应由 Worker 自己回；`wrangler dev` 下同样生效，所以冒烟是在正式 CSP 下跑的，并监听 `securitypolicyviolation`。
  - 游戏自己的 `_headers` 里目前只有缓存规则、没有 CSP；以后游戏加 CSP 时按平台这一份来，同样要放行 `static.cloudflareinsights.com` 的脚本。
- **日志**：不记 cookie、请求体和 `Authorization`；密码和恢复码只走请求体，不进 URL。线上 Workers Logs 关着（`observability.enabled: false`）；查问题用 `wrangler tail`
  （它把 `cookie`、`authorization` 头显示成 `REDACTED`，但 `cf-connecting-ip` 是原文；只是实时流，不保存）。要开 Workers Logs 先重新核对这一条。

### 5.3 开房、进房与认人（房间登记和入场票没有做）

- **开房**：游戏 Worker 的 `acceptCreate(request, env)`：查 `Origin`、经服务绑定问平台 `/api/me` 认人、过 `RoomMeter` 的名额（4.7），再按随机 6 位码经 DO RPC 建房（撞码换一个，最多 5 次）。成功 201 `{code}`，失败见 4.6。
- **进房**：`acceptJoin(request, env, code)`：校验房间码、查 `Origin`、认人，再用 kit 内部地址把身份交给房间（4.1）。认人和 15.8 的登录闸门一个做法（只转发 Cookie 和 `cf-connecting-ip`，3 秒超时），但分清两种失败：
  200 且 `user` 为 `null` 是**没登录**（4401，不重连）；其他状态码、不是 JSON、缺字段、超时、没有绑定是**平台暂时不可用**（1013，稍后重连）。两种都拒绝（fail-closed），分开是为了平台抖一下不会把正在打牌的人踢走。
- **为什么不做平台的房间登记和入场票**（`POST /api/rooms`、Ed25519 签名的一次性进房票）：好友小范围开房，进房多问一次 `/api/me`（带 cookie 时读 D1 一两行）就够了；
  按人的开房名额和猜码限制已由 kit 的 `RoomMeter` 在游戏 Worker 里做完（4.6、4.7），入场票要管签名密钥、改平台，换来的只是省掉这次调用。
  要做的触发条件：进房量大到这次调用显得贵，或需要跨游戏统一的"每人同时一个房间"。房间这边只是换一种认人方式（`packages/arcade-kit/src/auth.ts`）。
- **代价**：每次进房（含被房间拒掉的）都算平台 1 次调用，靠平台自己的限流兜底（4.6 残余风险、15.6）。
- **单独部署**（没有平台）：没有 `ARCADE` 绑定且 `GATE` 不是 `login` 时，kit 走独立模式，以游客身份认人（`guest.ts`）。

### 5.4 防刷与限流

主要防止被攻击、耗尽额度。免费版全账户每天 10 万次 Worker 请求、D1 每天 10 万行写入、500 万行读取（UTC 0 点重置），单库存储上限 500 MB。被刷光或写满就是全站接口不可用，所以每一层都先挡便宜的。

**哪层挡什么**：
- 能保住**请求额度**的只有网关：请求只要进了 Worker，哪怕立刻被拒，也算一次调用。所以 6.6 的停服档保得住 D1，**保不住请求额度**；脚本绕开浏览器狂刷时，最后一道是网关限速。
- 能保住 **D1 写额度和存储**的是持久限流、写入预算和存储档位（下面第 4 条和 6.6）。
- `Origin`、`X-Arcade` 这类检查只挡浏览器（5.2）。

1. **网关**：免费版有 1 条速率限制规则，已建（站点所在 zone 的 `http_ratelimit` 阶段）：范围是站点主机名的 `/api/*`，以及 `/games/*` 下含 `/room/`、`/rooms/`、以 `/rooms` 结尾或含 `/api/` 的路径（各游戏的开房、进房和自己的接口）；
   按 IP + 机房计，每 10 秒 60 次，超了阻断 10 秒（放到 60 是因为同一个 WiFi 下多人共用一个出口 IP）。被拦下的请求不进 Worker、不算调用。WebSocket 连上以后的消息网关管不到，靠房间的令牌桶和额度（4.6）。
   突发没实测（测试网络经代理）。遇到大规模刷量，维护者可临时在 WAF 里加自定义规则直接拦 `/api/*`。前提是请求经过 zone，所以平台 `workers_dev: false`（3 节）。
2. **进 Worker 后、碰 D1 之前的廉价检查**（完整顺序见 15.1）：Host → 方法和路径白名单 → 熔断档位（内存里）→ 写请求的 `X-Arcade` 和 `Origin` → 路径参数 → 请求体大小 → JSON 解析。任何一步不过就直接返回，不读不写 D1。
   **isolate 内存限流**：每个 isolate 在内存里给每个 IP 哈希一个令牌桶（匿名接口每分钟 10 次），并缓存"某个限流键已超限到某时"，命中直接 429；isolate 很多、随时回收，只是挡突发的第一道。
3. **匿名只开放极少的接口**：注册、登录、找回、`GET /api/me`（没带 cookie 时直接返回未登录，不碰 D1）。其余都要登录。注册先过内存令牌桶，再读开关（1 行读）：关着回 403、写 0 行。
4. **持久计数限流**：表 `rate_counters`，键形如 `<用途>:<对象>`，固定窗口计数，超了 429 并带 `Retry-After`。每条规则的上限和写入代价见 15.6。
   - **超限的请求不写行**：带条件的 UPSERT——`INSERT … ON CONFLICT(key) DO UPDATE SET count = count + 1 WHERE count < 上限`（窗口过期时重置）。已超限时条件不成立，**写入 0 行**（`test/d1-facts.test.ts` 实测）。
   - **失败计数锁着的时候再失败，也写 0 行**：`WHERE blocked_until <= now OR 窗口已过`，所以锁到期那一刻并发打进来的一批失败，最多写到重新锁上为止。登录失败和再验证失败都是这样。
   - **每新建一个计数行，之后 Cron 清理时还要再算 1 行**（7.2），能不新建就不新建：用户名不存在时不记失败计数。
   - **全站计数不单独写行**：`login:all`、`rec:all` 随 6.6 的计量一起上报，会滞后、可能超出几十次，但每次尝试少写 1 行。
   - 登录：每 IP 每小时 30 次（成败都算），全站每小时 300 次（**只算用户名存在的尝试**）；连续错 5 次后下一次要等 30 秒，之后每错一次翻倍，最长 1 小时，成功或找回成功清零；
     失败计数在**算 PBKDF2 之前**就占一次（锁着时 0 行、429），对了再清零，所以锁到期那一刻并发的一批只有一个能验密码。最坏情况是别人故意把某个用户名锁 1 小时，接受。
   - 全站名额只算用户名存在的：撞库要猜的是真账号；乱填的用户名伤不到任何账号，由每个 IP 的上限和令牌桶管。
   - 其余（注册、找回、存档、好友、屏蔽、交分、邀请码试码、管理）的数字见 15.6。
5. **Turnstile 不上**：国内可用性没测过。注册被刷到全站上限时，先靠网关规则和日上限顶住。
6. **全站兜底**（6.6）：D1 写入按类别分预算，一类用完只停这一类，不连累别的；再加存储档位和总量的只读、停服档。

**挡不住的**（接受）：
- **全站上限能被少数 IP 占满**：登录全站每小时 300 次、找回 100 次、注册每天 300 个，十来个 IP 就能占满，那段时间所有人**新登录不了、找回不了、注册不了**；已登录的玩家不受影响（会话 400 天），存档、好友、单机照常。
  按"先保额度"的优先级接受。应对：看到 429 激增时先在 WAF 里临时拦那几个 IP 段；需要的话改 `vars` 调高上限（走 PR）。
- **存档、排行榜预算能被小号用完**：那时只是存档或交分暂停到第二天；两类预算分开，刷榜不会把云存档挤停；邀请制下号都是管理员建或凭邀请码注册的，囤号更难。

### 5.5 云存档

- **范围**：只同步档案、战绩、教程标记；**不同步打到一半的那一局**；设置不同步。各游戏同步哪些槽写在各自的 AGENTS.md。
- **平台只存不透明的 JSON 和版本号 `rev`**，不懂内容；合并由游戏自己写。
- **接口**（15.3）：`GET /api/saves/<gameId>` 一次取回这个游戏的所有槽；`PUT /api/saves/<gameId>/<slot>` 带 `{baseRev, data}`，执行 `UPDATE … WHERE rev = baseRev`，没改到就 409 并带回云端当前版本，游戏合并后用新的 `baseRev` 重交。`baseRev = 0` 表示新建。
  - **预期账号**：PUT 的请求体、GET 的查询参数 `?userId=` 可以带"客户端以为自己是谁"，和会话不一致就 409 `wrong_user`，不读不写。因为别的标签页换了账号时，cookie 已经是新号、页面里还是旧号的数据，客户端只能缩小这个窗口，堵不干净。
- **上限**（以 `config.ts` 为准）：每槽 `data` 序列化后 ≤ 48 KB（留出 keepalive 的余量），每个游戏 ≤ 8 个槽，每人合计 ≤ 256 KB；槽名 `[a-z0-9-]{1,32}`。`gameId` 必须是 `platform/src/games.ts` 登记过的游戏（登记即生效，钱包白名单、保留用户名也从它派生）。
- **并发不冲破上限**：版本、10 秒间隔、每游戏槽数、每人合计大小，都写在同一条带条件的 SQL 里，没满足条件就一行都不写。覆盖已有的槽时合计按"换掉这个槽以后"算；合计超了也允许改小。
- **停增长档**（6.6）：停止新建存档槽，已有的槽覆盖只许不变大，否则 503 `busy`。
- **服务端限流**：同一个槽 10 秒内只收一次，每人每天 ≤ 500 次 PUT，超了 429。全站另有存档的每日写入预算和存储档位（6.6）。
- **存档接口不更新 `last_seen_at`**：只有 `GET /api/me` 才做（5.1）。所以游戏接入云存档时**必须调 `/api/me`**，否则只玩游戏、不开平台页的人会被当成一年没登录清理掉（7.3）。
- **游戏侧**（每个游戏一个 `cloud.ts`）：元数据存在 `<id>.cloud`，记 `{userId, 每槽的 rev, dirty}`；合并规则：集合取并集、计数取较大、布尔取"或"，合并前把本地数据备份到 `<id>.<slot>.pre-sync`；
  10 秒防抖上传，切到后台时用 `fetch(…, {keepalive: true})` 补传（keepalive 的 64 KB 是整个请求体上限，同页面所有在途请求共用，所以每槽 48 KB，切后台一次只补传一个槽，请求体超过 60 KB 不走 keepalive）；
  只在有 `__Host-arcade_li` 时才调接口；游戏里加一个云朵图标（未登录 / 已同步 / 同步中 / 待上传 / 已合并），点"未登录"跳 `/login?from=<id>`。

**游戏接入云存档的做法**（掼蛋的实现为准，其他游戏照做）：

1. **启动**：带着 `__Host-arcade_li` 才发请求。先 `GET /api/me`（顺带续 `last_seen_at`），拿到 `user.id` 和 `saves` 档位；再 `GET /api/saves/<id>?userId=<user.id>` 拉取合并。`/api/me` 返回 503 或 `saves: "paused"` 时本次打开暂停同步；`user` 为 null 或 401 按没登录处理。
2. **每次写都带账号**：每个 `PUT` 的请求体都带 `userId`（正常上传、409 后重交、切后台补传都带）。
3. **409 先看 `error`**：`conflict`：备份到 `pre-sync`、合并，用 `current.rev` 重交（`current` 为 null 用 0），**只重交一次**；`wrong_user`：不合并、不重试，走换号流程。
4. **换号**（`/api/me` 的 `user.id` 和 `<id>.cloud` 记的不同，或收到 `wrong_user`）：不问玩家、不弹提示、不上传旧数据。
   1. 把本机各槽备份到 `<id>.<slot>.pre-switch.<旧 userId>`（每个旧账号一份；已有同名备份时先合并再写）；
   2. 把本地各槽写成空档，元数据换成新账号（`wrong_user` 时先记成 `userId: null`），`rev`、`dirty` 清空，**立即存盘**，这样之后拉取失败、页面被关也不会把旧数据传上去；
   3. 再问 `/api/me`，拉新账号的云端数据（本地是空档，不算合并）；
   4. 以后再登录回某个账号、拉取完之后，把 `pre-switch.<该账号>` 按合并规则并回本地、标成待上传；上传成功后把备份**改名为 `.restored`**（不改名的话每次打开都会再并一次，会把"当前连胜"这类数反复抬回旧值）。

   理由：换账号基本就是"一台设备几个人用"，问玩家要不要合并，点错一次就把别人的战绩永久混进自己账号；不合并最坏只是本机暂时换成新账号的数据，旧的有备份。
5. **存储满时暂停，不清空**：备份写完要读回核对；有一个槽没存上就什么都不清、不拉新账号的数据，暂停同步，云朵加小红点说明"本机存储满了……"。宁可不同步，也不丢还没备份的数据。
6. **不算换号**：这台设备第一次登录（`<id>.cloud` 还没记账号）时，本机数据合并进他的账号；同一个账号退出再登录，退出期间玩出来的照常补传。
7. **上传节奏**：10 秒防抖，另外**同一个槽两次上传至少隔几分钟**（掼蛋 5 分钟），否则每局都改存档的游戏会碰到每天上限。切后台的补传接 `visibilitychange` 和 `pagehide`，同槽有请求在途时不重复发，离上次上传太近（掼蛋 3 分钟）就留到下次打开。
8. **其他回应**：429 按 `retryAfter` 按槽等；413 这个槽不再重试并提示；400 这个槽本次不再传；503 本次打开暂停；401 当作已退出；连不上或回来的不是 JSON 保留待上传。
9. **复查身份**：回到前台、窗口拿到焦点时，离上次**尝试**确认身份超过 1 分钟就再问一次 `/api/me`，发现换号走第 4 条。
10. **多个标签页**：在 `storage` 事件里合并元数据（`rev` 取大、待上传取并集，那边换了号这边跟着换）；换号前先读存盘的元数据，别的页已经处理过就只跟上。
11. **界面**：只有平台明确说没登录才显示"未登录"并引导登录；连不上、停服时显示"待上传"加小红点，点了只给说明，不叫人去登录（15.1）。

### 5.6 好友

代码在 `platform/worker/api/friends.ts`，接口见 15.4。

- **好友码**：每人一个 8 位好友码（Crockford base32，约 40 bit），可换新（每天 ≤ 3 次），换了旧码和旧链接立刻失效。输入规则同恢复码；格式不对直接 404，不计数、不碰库。**不按昵称搜**（防骚扰，也不暴露站上有哪些人）。
- **链接 `/f/<码>`**：显示对方的头像字和昵称，按钮随关系变；码找不到时说"可能对方换了新的"。每打开一次计一次查码（`fcode`，每天 ≤ 100 次，没找到也计），防枚举；只读档或"好友与资料"类预算用完时不给查（503 `busy`），好友列表照常。
- **请求**：对方在好友页接受或拒绝，自己可撤回。每天发 ≤ 30 个（撤回或被拒都不退还）；用发请求的接口猜码、码不存在时也计一次 `fcode`。待处理的请求**我发出的、对方收到的各 ≤ 20 个**，好友 ≤ 200 个。上限条件都写进 SQL，并发冲不破。
- **互发请求自动成为好友**：对方已向我发过请求时，我再发就直接成为好友；两人**同时**互发时，后到的撞主键后再查一次，是对方发来的待处理请求就同样直接成为好友（`platform/test/friends.test.ts` 让 6 对人同时互发）。任何一方好友数满了回 422 `limit_reached`。
- **只给公开资料**：对别人只展示昵称、头像和"今天来过 / N 天前来过"（按北京时间日历天算，不给精确时间），**不展示用户名**（用户名是登录凭据的一半）。
- **屏蔽**：屏蔽时删掉双方之间的好友关系或请求（含搭子战绩）；被屏蔽的人照常能发请求（返回 `pending` 并写入请求行，他看不出自己被屏蔽），屏蔽方的"收到的请求"里不显示这些请求、也接受不了，且这些请求**不占**屏蔽方的 20 个名额；
  屏蔽方自己想加被屏蔽的人回 422 `unblock_first`。屏蔽和解除每天合计 ≤ 30 次（不限的话"屏蔽 → 解除"来回刷会把"好友与资料"一天的预算刷光），已屏蔽着再屏蔽不计数；屏蔽的人数本身不设上限。
- **注销时删干净**：好友、请求、两个方向的屏蔽、相关计数（`freq`、`fcode`、`fcnew`、`block`），都在 `deleteUserStatements` 里（7.3）。
- **在线状态、邀请、动态、搭子战绩**：见 15.14–15.19（行为规范和分期在 `docs/social.md`）。

### 5.7 平台界面

- **页面**（React，没有路由库，约 40 行的极简路由，线上靠静态资源的单页回退）：`/login`（登录；注册页签只在注册开着或带了邀请码时才有）、`/forgot`（用户名 + 恢复码 + 新密码重设，成功后给新恢复码）、
  `/me`（昵称、好友码；各游戏云存档；账号安全：改密码、换恢复码、退出其他设备、注销，都要再输一次当前密码，注销也可改用恢复码）、`/privacy`、`/admin`、`/friends`、`/f/<码>`、`/i/<码>`（邀请码注册）、
  `/wallet`、`/boards`、`/me/stats`、`/u/<用户 id>`。首页右上角：没登录是"登录"，登录后是头像加昵称；管理员多一个"管理"链接。电脑版（≥960）两三栏、手机单列。
- `/login?from=<id>`：`from` 只认 `platform/src/games.ts` 白名单里的游戏 id（以及 `friends`、`f/<码>`），登录后整页跳回。别的值一律回首页，防止被拿来跳到外站。
- `/login?next=<路径>`（给游戏"叫朋友来"和闸门用）：登录或注册完成后整页跳到 `next`，查询参数原样带回（比如房间码）。游戏照着拼：`'/login?next=' + encodeURIComponent(location.pathname + location.search)`；闸门 302 时同样拼。
  - **只认**：以 `/` 开头、不超过 200 个字符的本站路径，落在 `/games/…` 或平台自己的页面（`/`、`/friends`、`/f/<码>`、`/me`、`/me/<页>`、`/wallet`、`/boards`、`/privacy`、`/admin`）。不认登录页和找回页，免得绕回来。
  - **不认**：`//` 开头、带协议、带反斜杠、带空白或控制字符的，以及按本站地址解析后不在上面几处的（如 `/games/../api/me`）。不认就当没带，按 `from` 处理；同时带两个时 `next` 优先。代码 `platform/src/next.ts` 的 `safeNext`。
- **请求数**：只有带登录提示 cookie 才问 `/api/me`；没登录的访客首页零个 `/api` 请求。登录页问一次取 `registration`，没问到按"关闭"显示。
- **暗上线开关**：以后要再暗上线，用构建期常量、不放 Worker 的 `vars`（平台页是静态资源，读 `vars` 会让每个访客多一次 Worker 请求）。
- **恢复码卡片**（注册、找回、换恢复码、管理员建号共用）：可复制、可存成图片（浏览器里用 canvas 现画），勾"我已经存好了"才能继续；没勾时离开页面、退出登录都先提醒。
- **档位与错误的显示**：只读档：写表单的提交按钮灰掉，"退出登录"照常，提示"服务器有点忙，现在只能看、不能改"；`saves: 'paused'` 时云存档卡片标"云存档先暂停了"；
  停服档（接口明确回了 `busy`）：提示"账号服务暂时休息"，**不放登录入口**；连不上（断网，或回来的不是 JSON）：显示"连不上服务器"横幅带"重试"，同样不放登录入口——**只有接口回了 `busy` 才算停服**（15.1）；
  任何请求回 401，前端立刻清掉登录状态；`bad_credentials` 按场景换说法。手机上点击区高度不小于 44 px。文字中文大白话，不写术语。
- **隐私说明**（`src/pages/Privacy.tsx`，页面开头的注释写了天数出自 `config.ts`、`cron.ts`，改那边要同步改这里；每一条只写代码里确实这样做的事）：
  顶部承诺"不放广告，也不卖数据；除了'访问统计'里交给 Cloudflare 的匿名统计，不给别人"；存的：用户名和昵称、只存打乱后的密码和恢复码、登录记录（最后一次来过以后最多留 400 天）、云存档、好友码和好友关系和屏蔽、
  排行榜每榜只留最好一次（登录的人看得到昵称和分数，每日榜 60 天后删）、战绩对登录的人公开、最近一次来的时间精确到小时左右、邀请关系；不存的：手机号、邮箱、真实姓名、IP 原文（防刷计数里是 HMAC，一般 3 天内清掉）、访问日志；
  访问统计用 Cloudflare Web Analytics（按 Cloudflare 官方说法不用 cookie、不认出具体是谁）；怎么删：注销，或一年没来过自动删（管理员除外），数据库备份 30 天内过期。
- **界面冒烟**见第 8 节（`npm run smoke`）。

### 5.8 邀请制、管理员与游戏登录闸门

测试期是**邀请制**：不登录不能玩，公开注册默认关，账号由管理员建，或凭邀请码注册（15.20）。

- **注册开关**（改了不用重新部署）：
  - **D1 里的开关**：表 `settings` 的 `registration` 一行，值 `open` / `closed`；**没有这一行按关**，迁移不放初始数据。
  - **紧急总闸** `wrangler.jsonc` 的 `vars.REGISTRATION`：只有 `"switch"`（不分大小写、去首尾空白）才听 D1 的开关；`"off"`、没设、写错一律**强制关**（fail-closed）。线上配的是 `"switch"`。
  - **怎么改**：管理页 `/admin` 最上面的"开放注册"（点了先弹确认）、`npm run admin -- registration open|close|status`、或 `POST /api/admin/settings/registration`（15.7）。总闸关着时开关照样记下，界面和接口都说明"暂时不起作用"（`forcedOff: true`）。
  - **注册时的顺序**：IP 哈希 → isolate 内存令牌桶（超了 429、不碰 D1）→ 读开关（**每次读最新值**）→ 校验请求体 → 试邀请码 → `reg:ip`、`reg:all` 计数……关着回 403 `registration_closed`，**写 0 行**；读开关失败也按关，回 403。
  - `GET /api/me` 带 `registration`，用每个 isolate **30 秒的内存缓存**（游戏闸门每次打开首页都问，不想给每次访问加一次 D1 读）；停服档或读不到时按关。
- **管理员**：`users.role`（`user` | `admin`）。管理员只能由命令行建号工具（Bearer）创建，没有改角色的接口；Cron 不清理管理员。管理员在 `/api/me` 的 `user` 里多一个 `isAdmin: true`。
- **管理接口 `/api/admin/*`**（请求和响应见 15.7）有两种认证（`worker/api/admin.ts`）：
  1. **Bearer 令牌**（命令行建号工具用）：`Authorization: Bearer <ADMIN_TOKEN>`。`ADMIN_TOKEN` 是 Secret，值写成 `<kid>:<至少 16 位随机串>`，没设或格式不对时谁的令牌都不认。两边各算 SHA-256 再 `timingSafeEqual` 比较。
     **先占名额再比对**（让比对次数有硬上限，也不给"对 / 错"两种不同的限流信号）：只读档（503）或账号安全类预算用完（429）时不比对、写 0 行；
     先只读查两个计数（每 IP 每小时 `adminFailPerIpHour` 10 次、全站每小时 `adminFailAllHour` 30 次），满了就 429、不比对；再把两个计数各占一个名额（带条件的 UPSERT，并发在这里排队）；
     比对成功就把两个名额还回去（共写 4 行），失败留着当失败记录（写 2 行，回 401）。不看 `X-Arcade` 和 `Origin`；Bearer 只对 `/api/admin/*` 有效。
  2. **管理员会话**：`__Host-sid` 对应的用户是管理员；写请求照常要 `X-Arcade` 和 `Origin`。没登录 401，普通用户 403 `not_admin`。
- **权限分级**：`role: 'admin'` 的账号只有 Bearer 能建；**会话管理员不能动任何管理员账号，包括自己**（重设密码、删号回 403 `admin_protected`；删自己回 409 `cannot_delete_self`）——管理接口不要求再输密码，
  偷到管理员 cookie 的人不该能把真管理员锁在外面；不能删最后一个管理员（409 `last_admin`）。
- **每日上限**：每个管理员（令牌单独一份）每天最多 `adminPerDay`（300）次成功的**写操作**；记在"账号安全"类预算。
- **生成的密码**：不给 `password` 时生成"3 个常用英文短词 + 2 位数字"（至少 14 位）；生成的密码和恢复码只在这次响应里返回一次。
- **管理界面 `/admin`**：只有管理员能进。建号表单、账号列表（重设密码、删号要先勾确认、"钱包和战绩"）、注册开关、邀请额度和邀请码、大厅公告、钱包规则、筹码统计和今日概况。管理员那一行只显示"管理员账号要用本机建号工具来改"。
  建号或重设成功后只显示一张卡片（用户名、密码、恢复码，可"复制成一段话"），离开会提醒。
- **命令行建号工具** `platform/tools/admin.ts`，`npm run admin -- <命令>`（在 `platform/` 下）：`list`、`create <用户名> <昵称> [--admin] [--password=…]`、`reset <用户名> [--new-recovery-code] [--password=…]`、`registration open|close|status`；
  `--base=` 指定接口地址，只许 https 或本机 http；令牌只从环境变量 `ARCADE_ADMIN_TOKEN` 读，不读文件、不打印、不放命令行。
- **游戏登录闸门**：游戏要登录才能进，调用约定见 15.8。

### 5.9 钱包

方案正本是 `docs/economy.md`；这里写平台怎么实现、写几行。代码在 `platform/worker/api/wallet.ts`（类型和纯函数的账）、`wallet-store.ts`（读写、规则、统计）、`wallet-api.ts`（浏览器和管理页接口）、`platform/worker/wallet-service.ts`（给游戏的 RPC），测试 `platform/test/wallet.test.ts`。

- **存储**：表 `wallets`，一人一行，状态整个放在 `state`（JSON）里：余额、各游戏桌上那一份（`游戏:ref` 为 key，含档位、金额、`mode`、带入时间、到期时间）、补给日期、当天和前一天的计数、
  最近 32 个操作 id 和结果、最近 16 个到期退回的 `游戏:ref`、`career`（5.10）、`ledger`（最近 30 笔余额变动）、`adminLog`。
  - **为什么一行 JSON**：每个动作都要同时改余额、桌上那一份和当天计数，拆成几张表每次要写好几行；一行 JSON 每次只写 1 行，状态几 KB。
  - **并发**：用 `rev` 做乐观并发 `UPDATE … WHERE user_id = ? AND rev = ?`，写 0 行说明被抢先，重读重算再写，最多 4 次，还不行回 `busy`；第一次建行用 `INSERT … ON CONFLICT DO NOTHING`。遇到 D1 标"重试即可"的暂时性错误，平台自己退避重试最多 3 次。
  - **新号**：注册时不建行，第一次带入（或领补给）时才建，送 10,000；没有钱包的人看钱包是余额 10,000、`fresh: true`，不写库。
  - **换日**：北京时间 0 点。碰钱包时发现过了 0 点，就把当天计数挪到"前一天"。跨零点还在桌上的 client 那一份算进新一天这个游戏的带入，否则 23:50 带入、00:10 结回时本金会被当成赢的。
- **给游戏的 RPC**：`WalletService`（`WorkerEntrypoint`），参数是一个对象，回 `{ ok: true, wallet, credited?, capped?, dup? }` 或 `{ ok: false, error, wallet? }`。业务拒绝都用返回值、不抛异常。

  | 方法 | 参数 | 成功 | 写入 |
  |---|---|---|---|
  | `view(userId)` | — | 钱包 | 0；有到期退回时 1 |
  | `buyin(req)` | `userId, game, ref, tier, amount, until, mode, op` | 余额扣掉 `amount`，记到这个游戏桌上那一份 | 1 |
  | `settle(req)` | `userId, game, ref, amount, mode, op`，可选 `stats`（5.10） | `credited` 进余额（client 模式超出每日上限的在 `capped` 里，不进），清掉那一份 | 1 |
  | `refund(req)` | `userId, game, ref, mode, op` | 那一份原样退回，清掉 | 1 |
  | `together(req)` | `op, players: [{userId, team?, win}]` | 搭子战绩，一场整桌报一次（15.19）；回 `pairs` | 每对 1–2 行，记在排行榜类 |

  - `game` 是登记的游戏 id；`tier` 是 `small` / `mid` / `big` / `lux`（一份 2,000 / 10,000 / 50,000 / 200,000，`economy.md` 第 2 节）；`ref`、`op` 是 8–64 位 `[A-Za-z0-9_-]`；`amount`、`until`（Unix 毫秒）是非负安全整数；
    `mode` 是 `server`（结果由服务端说了算，如好友房）或 `client`（浏览器算的）。
  - **重复请求**：同一个游戏的同一个 `op` 再来，什么都不改、写 0 行，回第一次的结果并带 `dup: true`（按 `游戏:op` 分开记；补码的带入另记在那一份上最近 16 个）。
    **重复要是同一件事**：每个 `op` 连同指纹（类型、`mode`、`ref`，带入再加 `tier`）记下，指纹不同回 `op_conflict`、写 0 行——单机接口的 `op` 由浏览器给、好友房的 `op` 能猜，只认 `op` 的话，有人先用单机占住房间接下来的 `op`，房间补码就被当成已扣过。
  - **出错重发是安全的**：回了 `internal`（或调用抛错、超时）时，拿**同一个 `op`** 再调一次：写成了的回第一次的结果，没写成的照常做。
  - **带入**：每次 1 到一份（`bad_amount`）；`until` 已过回 `bad_until`，超过 24 小时按 24 小时算。同一个 `ref` 再带入是补码，要同一档（`at_table`）、同一 `mode`（`bad_mode`），加到那一份上，到期时间取晚的；
    新开一份、补码都只要余额 ≥ 这次的 `amount`（`no_funds`）。到期退回过的 `ref` 不能再开（`expired`）。
  - **结回**：要有这个游戏、这个 `ref` 的那一份，`mode` 一致。没有回 `no_stake`（已到期退回过的回 `expired`）——钱包里没带入就没有结回。`amount` 可以是 0，最多是带上桌的加 20 份（只防写错）。
  - **错误码**：`bad_request`、`unknown_game`、`bad_game`、`no_user`、`limit`（今天写满 1,000 次）、`no_funds`、`at_table`、`bad_amount`、`bad_until`、`bad_mode`、`no_stake`、`expired`、`op_conflict`、`busy`、`internal`。被拒时一般带当前的 `wallet`。
- **游戏怎么接**：在游戏 `wrangler.jsonc` 里加一个服务绑定（和认人的 `ARCADE` 分开）：`"services": [{ "binding": "WALLET", "service": "arcade", "entrypoint": "WalletService", "props": { "game": "texas" } }]`；
  `await env.WALLET.buyin({ userId, game: 'texas', ref: roomId, tier: 'small', amount: 2_000, until: Date.now() + 6 * 3_600_000, mode: 'server', op })`。平台要先部署（带 `WalletService` 的版本），游戏才能部署带这个绑定的版本。
- **防别的游戏冒充 game id**：只有本账号里的 Worker 能声明到 `arcade` 的服务绑定，公网和浏览器碰不到 RPC（`/api` 里没有带入、结回、放弃这几条路，测试锁住）。**绑定上必须写 `props.game`**，参数里的 `game` 必须和它一致，
  否则四个方法（含 `view`）一律回 `bad_game`、不碰库。`props` 写在调用方自己的部署配置里，游戏代码在运行时改不了。每个游戏只能动自己那一份，结回、放弃还要对得上 `ref`。信任边界就是这个账号：账号里的 Worker 都经 PR 审阅后由 CI 部署。
- **服务绑定 RPC 在免费版**：能用；不另收请求费（游戏调平台算一个请求，两边 CPU 合计；平台 6.6 计量照样算 1 次调用）；算调用方的子请求（免费版每次调用最多 50 个）；CPU 每次 10 ms，钱包一次操作远低于它；
  异常只保证 `name` 和 `message`，所以业务错误都用返回值；命名入口要从平台主模块导出。
- **计量和熔断**：每次 RPC 算平台 1 次调用；写入记在"钱包"类预算（6.6，6,000 行）。停服档全停（`busy`）；只读档或钱包类预算用完：停带入和领补给，**结回、放弃照收**（桌上的筹码总要能回来），看钱包照常；
  停增长档：不建新钱包，已有的照常。
- **每人每天 1,000 次写入**（北京时间，各游戏合计，记在钱包行里）：到了上限不能带入（`limit`）、不能领补给（429）；结回、放弃、到期退回不受限。
- **管理员可调的规则**：补给额（默认 2,000）、单机每日净赢份数（默认 10）、新号送多少（默认 10,000）、管理员单次调整上限（默认 ±1,000,000）这四个数存在 `settings` 的 `wallet_rules` 一行里（连同最近 20 次改动记录），管理页改了即时生效（15.7）。钱包按 30 秒缓存读这一行，读不到用代码默认值。
- **client 模式的每日上限**（`economy.md` 第 4 节）：每个游戏每天净赢 ≤ 10 份。净赢 = 当天这个游戏 client 模式结回进钱包的 − 带入的；份 = 当天这个游戏带上桌的各份里最大的那一份，每份取 min(档位一份, 实际带上桌的)；
  结回时最多进到"净赢正好 10 份"，超出的在 `capped` 里不进钱包；**带上桌的那一份总能拿回来**（到顶以后至少退回带入的数）；放弃、到期退回把那一份从"带入"里减回去，否则转几圈能撑大上限；server 模式（好友房）不设上限。
- **浏览器接口**（15.9）：`GET /api/wallet` 看自己的钱包；`POST /api/wallet/relief` 领每日补给（余额加桌上的不到补给额、北京时间今天没领过，就补到补给额），按 5.2 的 CSRF 规矩，一天只能领一次。大厅有筹码在桌上时提醒并直达游戏，`canRelief` 时就地放"领补给"按钮。
- **到期退回**：每次碰钱包时，先把过了 `until` 的那一份原样退回、记下 `游戏:ref`。之后这个 `ref` 来结回、放弃、带入都回 `expired`。被拒的操作不写库，到期退回留到下次能写时。
- **统计**（`economy.md` 第 6 节）：每天的 Cron（7.3）先记一行北京时间昨天的全站统计到 `wallet_stats`（1 行，系统类）：全站筹码总量、钱包数、新号送的、补给、各游戏的带入 / 结回 / 退回 / 到顶没进。管理页显示最近 30 天，"庄家"一列 = 带入 − 结回 − 退回。
- **删号**：钱包行在 `deleteUserStatements` 里（7.3）。`wallet_stats` 只有全站合计，不带人。
- **管理员调整**：`GET /api/admin/wallet/<用户名>` 查人（钱包、`career`、`ledger`、调整记录）；`POST /api/admin/wallet/adjust {username, amount, note?}` 正数加负数扣，单次上限见上；`GET /api/admin/wallet-adjustments` 看全站最近 10 次。
  只认管理员会话（令牌 403），按 5.2 做 CSRF，记在账号安全类；每次只写钱包那 1 行，加到余额上限、扣到 0 为止，不碰桌上那一份；记录存在钱包 state 的 `adminLog`（每人最近 20 条）。
- **流水**：钱包 state 里的 `ledger` 记每人最近 30 笔余额变动 `{"at", "t", "g"?, "a", "capped"?}`，`t` 是 `grant`、`buyin`、`settle`、`refund`、`expire`、`relief`、`admin`。跟着钱包那 1 行一起写，不新增行；本人的 `GET /api/wallet` 回自己的，游戏的 RPC 不回。

### 5.10 战绩（career）

平台要把游戏串起来：战绩页、排行榜、称号墙。数据从结回时带上来，跟着钱包那一行一起写，不新增行、不新增请求。

- **怎么带**：钱包 RPC 的 `settle(req)` 多一个可选字段 `stats`（这一份的小结）。游戏自己的 `/api/stake` 之类路由只原样转发，不改不补。不带 `stats` 也照常结回，只是局数、称号不记。
- **给游戏的类型**（游戏不能 import 平台代码，照抄）：

  ```ts
  /** settle 可选带的这一份小结。JSON 后 ≤ 256 字节；不合格就整份忽略，结回照常，回话里 statsIgnored 说原因 */
  export interface SettleStats {
    /** 这一份里打了几局（开盘：一整局半年；掼蛋：副数；德州：手数）：非负整数，超过 1,000 按 1,000 算 */
    rounds: number;
    /** 其中赢了几局：非负整数，超过 rounds 按 rounds 算。什么算赢由游戏定 */
    wins: number;
    /** 这一份里最大的一把净赢了多少筹码：非负整数；记的时候截到不超过这一份结回的 amount */
    best: number;
    /** 这一份里拿到的称号 id，最多 5 个，每个 1–24 位 [a-z0-9_] 且以字母开头；拿过的再报也行，平台去重 */
    titles?: string[];
    /** 游戏自定义的数，max 和 sum 合计最多 3 个；key 1–16 位 [a-z0-9_] 且以字母开头，值是安全整数。max 取历史最大，sum 累加 */
    max?: Record<string, number>;
    sum?: Record<string, number>;
  }
  ```

  回话多一个可选的 `statsIgnored: 'too_big' | 'bad_stats'`：JSON 超过 256 字节或形状不对时整份忽略，钱照常结。局数、赢的局数、最大一把超出时是截断不是忽略。重复的 `op` 回第一次的结果，小结不会记两次。
- **存在哪**：钱包 state 里的 `career`，按游戏分：`n`（结回过几份）、`net`（累计净赢）、`wk`（本周周一日期）、`wnet`（本周净赢，`wk` 不是这周就当 0，不用 Cron 清零）、`rounds`、`wins`、`best`、
  `titles`（id → 第一次拿到的时间，每游戏最多 64 个）、`max` / `sum`（自定义数，每游戏最多 8 个 key）。
  - 净赢、本周净赢由平台按钱算，**不靠小结**：放弃、到期退回不算一份、不动净赢；client 模式到顶没进钱包的不算赢。总的本周净赢在查询时按各游戏 `wk` 是这周的 `wnet` 求和。
- **称号的名字**：小结里只有 id。每个游戏放一个静态文件 `/games/<id>/titles.json`（同域公开 HTTP 接口），格式 `{ "bluff_king": { "name": "诈唬王", "desc": "一句话说怎么拿到的" } }`，`name` 建议 2–6 个字。
  平台的称号墙在浏览器里读：文件最多 32 KB、3 秒超时；读不到或没有这个 id 时显示"神秘称号"。加新称号只改游戏自己的文件。
- **谁看得到**：`career` 全部字段对登录的人公开；余额、桌上的、操作记录、管理员调整只有本人和管理员看得到。
- **成本**：结回带不带小结、小结被忽略，请求数和写入都不变（钱包那 1 行）。

## 6. 费用与额度防护

Cloudflare 没有官方的花费硬上限：预算提醒只发邮件，而且晚一天才到；GraphQL 数据又会延迟、会少算。现在跑在免费版，真正要防的是**额度被刷光**（超了是操作失败，不是多花钱）；开付费版之后才有"花钱"的问题（6.2、6.5）。

### 6.1 现有的几层

| 层 | 做什么 | 反应速度 |
|---|---|---|
| ① 硬限制 | 4.6 的各项上限。防的是 bug 失控，这是最大的风险 | 立即 |
| ② 房间计量 | 每个游戏 Worker 的 `RoomMeter`（4.7）：按人和全站的开房名额、当天写入到 `busyWrites` 不开新房、到 `stopWrites` 收场 | 立即 |
| ③ 平台接口计量 | 6.6：平台自己数调用次数和 D1 读写行数，分类预算 + 总量档位（正常 / 停增长 / 只读 / 停服） | 约 1 分钟，到 80% 后 1 秒 |
| ④ 网关限速与紧急开关 | 5.4 的网关规则；`API_MODE` Secret（6.6）一键只读或停服 | 立即 / 人工 |
| 另加 | Cloudflare 预算邮件（天级） | 天级 |

### 6.2 按账单自计量、GraphQL 对账（没有做）

原设计：一个全局 Meter DO 按官方单价（请求每百万次 0.15 美元、时长每百万 GB-s 12.5 美元、写入行每百万 1 美元，含向上取整）累计本计费周期的估算花费，每小时用 GraphQL 对账。
**没有做，因为**：现在是免费版，额度（天级、全账户共享）比金额更先到顶，②③已经管住了；GraphQL 数据又不可靠（第 2 节）。
**开付费版时再做**，并把 6.6 的档位阈值改成按费用算。

### 6.3 熔断档位

现在的档位就是 6.6 的"总量档位"（正常 / 停增长 / 只读 / 停服，按天，UTC）加 kit 的 `busyWrites` / `stopWrites`。按金额的"限流 6–8 美元、停服 8 美元以上"是付费版设想，阈值留 2 美元余量（自计量会漏掉 Worker 请求、D1 和其他 Worker，
GraphQL 又会少算），目标是尽量不超过 10 美元，尽力而为、不是精确到分的保证。

### 6.4 墓碑版本（没有做）

单纯删路由不能止损：删掉 `/ws` 路由后请求会落到更宽的 `/games/<id>/*`，已连上的连接和房间闹钟也根本不经过路由。原设想是 CI 每次发布时多上传一个"墓碑"版本（房间收到任何事件就关连接、删闹钟、清存储，入口对 `/ws`、`/api` 一律 503），
Cron 判定需要时把它切到 100%。**没有做，因为**现阶段免费版超额自己就会失败，kit 的 `stopWrites` 已能让房间体面收场；`ctx.abort()` 和 `API_MODE` 够应急。开付费版前要补做并演练（带 DO 的 Worker 能否预传版本再切换、休眠房间多久换上墓碑代码）。

### 6.5 费用估算（开付费版时参考）

4 真人桌、30 分钟、保守 1:1 口径：每步 2 行，约 450 行；另有平台请求约 30 次、D1 写约 5 行。

| 规模 | 免费版 | 付费版每月 |
|---|---|---|
| 每天 ≤ 200 桌 | 够用。最先到顶的是写入行，每天 10 万行约合 220 桌；请求每天 10 万次约合 430 桌 | 5 美元 |
| 每月 1 万桌 | 不够（日峰值会超） | 约 5.3 美元（套餐含约 4,300 桌） |
| 每月 10 万桌 | 不够 | 约 8.5 美元：请求约 3.5 美元；写入约 4,500 万行，刚好在套餐的 5,000 万行以内 |

- 10 万桌这一档对写入规则很敏感：每步写 3 行就会多出约 17 美元，这是第 4.2 节要设硬规则的原因。AI 补位桌必须先做到批量出牌（4.4），否则一桌约 671 次请求。时长在这些规模下都远低于套餐含量。
- 一次交分：平台 Worker 请求 1 次，D1 写 1–3 行（7.2），比一桌掼蛋便宜两个数量级。

### 6.6 平台接口的最小计量与熔断

防的是免费版的**日额度和存储**被刷光。它保得住 D1，保不住 Worker 请求额度：被拒的请求也算一次调用，那一层靠网关（5.4）。

- **计什么**：平台 Worker 的调用次数（`/api/*` 和 Cron 都算，纯静态资源不进 Worker 不算）；D1 写入行数，**按类别分开记**（每次 D1 调用后把 `meta.rows_written` 记到接口所属类别，计量和 Cron 自己的写入记"系统"类）；
  D1 读取行数；库大小（取最近一次 D1 调用的 `meta.size_after`，整库字节数）；登录、找回的尝试次数。
- **怎么计**：每个 isolate 在内存里攒增量，满 50 次调用（匿名接口的尝试满 10 次）或离上次上报超过 60 秒（在下一个请求里用 `ctx.waitUntil` 顺带做），就用一条 UPSERT 合进 D1 表 `meter_hourly`（每个 UTC 小时一行），
  再读一次当天各小时的合计，算出档位缓存在内存里；isolate 处理第一个请求时先上报一次拿档位。约每 50 次调用写 1 行（约 2%）；isolate 被回收时最多丢 49 次调用的计数，所以总数**偏低**，阈值按"偏低"留余量。
  **上报失败就停（fail-closed）**：这个 isolate 进停服档，之后每 10 秒最多重试一次。
- **`vars.LIMITS` 的合并规则**：按项深合并，只写 `readonly.calls` 不影响同组其他项；每个值必须是正整数（只有 `meterEagerRatio` 可以是小数，`acctOverflow` 可以是 0），否则回退默认值并记日志（小数的迭代次数会写进哈希串、以后验不过）。
- **D1 写入的分类预算**（每天，`config.ts` 的 `budget`，线上可在 `vars.LIMITS.budget` 按项调；合计 40,000，和只读档的 50,000 之间留 1 万行余量，吸收上报滞后和账号安全类最多 3,000 行的超额）：

  | 类别 | 包含的接口 | 每天预算（行） | 用完了 |
  |---|---|---|---|
  | 注册 `reg` | `POST /api/auth/register`（含带码注册） | 2,700 | 只停注册（= `reg:all` 300 个 × 9 行） |
  | 登录找回 `auth` | 登录、找回 | 9,000 | 只停这两个；已登录的玩家照常存档、看好友 |
  | 存档 `save` | `PUT /api/saves/…` | 4,300 | 只停存档写入，第二天恢复；`/api/me` 的 `saves` 变成 `paused` |
  | 好友与资料 `social` | 好友、屏蔽、查好友码（要计数，所以算写）、改昵称和开关、换好友码、邀请码生成和撤回，以及顺带的 `last_seen_at`、续期 | 5,000 | 只停这一类；查好友码也停（503），好友列表照常 |
  | 账号安全 `acct` | 退出、改密码、换恢复码、退出其他设备、注销、再验证失败计数、管理接口 | 2,000 | 停换恢复码；改密码、退出其他设备只放行每人每天 `acct` 上限以内的，另有 3,000 行的超额封顶；退出、注销照做 |
  | 排行榜 `board` | `POST /api/scores`、异步挑战的发起和交成绩、搭子战绩 `together()` | 2,500 | 只停这些写（503 `busy`），读榜、云存档照常 |
  | 钱包 `wallet` | 游戏经 RPC 的带入、结回、放弃，看钱包时的到期退回，`POST /api/wallet/relief` | 6,000 | 停带入和领补给；结回、放弃、看钱包照常（桌上的筹码总要能回来） |
  | 在线 `live` | `POST /api/presence`、好友邀请、好友动态和赞 | 4,000 | 不报错、不写，照样回 204（好友那边慢慢变成"几分钟前来过"）；只读档同样静默 |
  | 监控 `mon` | `POST /api/client-error`、每 5 分钟的巡检状态（第 16 节） | 1,000 | 报错不再计数、静默 204；巡检状态不再更新（`/api/monitor` 的 `cron` 变成失败，告警会报出来） |
  | 系统 `sys` | 计量上报、Cron 清理、每天的筹码统计 | 3,500 | Cron 当天停止清理和统计；计量上报不停 |

  - 一类用完只停这一类（503 `busy`），不连累别的。尤其是匿名接口被刷时，已登录的玩家照常存档；刷榜也不会把云存档挤停。只拦写请求：读榜、读存档、好友列表这些 GET 不受类别预算影响。
  - **账号安全类单独一份，用完也不拦关键操作**：改密码、换恢复码、退出其他设备不管预算剩多少，都受每人每天 `acct:<userId>` 10 次的上限，每次 1 行；预算用完后换恢复码停，改密码、退出其他设备只放行上限以内的，
    超出预算的部分另有 3,000 行封顶，到顶后这两个也停；注销照做（每个账号只有一次）；退出照做。连超额封顶也用完时，注销仍放行，但失败计数写不进库了：库里这个窗口已错满 `failFree` 次的不再验密码、直接 429，
    猜错一次就在本 isolate 内存里把这个用户锁到 UTC 当天结束，也是 429、不写行（否则并发的错密码注销能把全站推进只读档，或让偷了 cookie 的人不计次数地猜密码）。
  - **退出在任何档位都能用**：只读档照样删会话、清 cookie；停服档不碰 D1，只清 cookie。
- **上报滞后和 80% 切换**：平时全站计数最多滞后"49 × 同时活跃的 isolate 数"次调用。任何一项（全站每小时上限、某类预算、总量档位）用到 80% 之后，本 isolate 只要有业务写入或匿名尝试就**立即上报**，两次至少隔 `meterEagerMinMs`（1 秒）；
  上报自己写的那 1 行系统类不算"业务写入"（否则在阈值附近空转）；只有调用次数、没有写入的请求（404、403、匿名 `GET /api/me` 等）不触发（免得靠刷便宜请求放大写入）。
  **停服档不立即上报**，只按 `meterFlushMs`（60 秒）报，每个 isolate 每分钟最多写 1 行。**冷启动**：isolate 还没拿到档位时，并发的请求等第一次上报完成，最多等 `meterFlushTimeoutMs`（3 秒），超时按上报失败处理（停服 503）。
  各项上限因此都可能被多放进一点，分类预算合计和只读档之间的 1 万行余量就是留给它的，7.2 的最坏情况也按这个算。
- **总量档位**（按 UTC 天计，阈值在 `vars.LIMITS` 里可调）：

  | 档 | 条件（默认） | `/api` 怎么办 |
  |---|---|---|
  | 正常 | 下面的都没到 | 照常（各类预算单独管） |
  | 停增长 | 库大小 ≥ 300 MB | 停注册、交分和新建存档槽（`baseRev` 为 0 一律 503 `busy`，不判冲突）；已有的槽覆盖只许不变大；读榜照常 |
  | 只读 | 调用 ≥ 40,000，或 D1 写入合计 ≥ 50,000，或读取 ≥ 300 万行，或库大小 ≥ 400 MB | 所有写接口（含注册、登录、交分）503 `busy`，只有退出照常删会话、清 cookie；`GET /api/me`、读存档、读好友、读榜照常，但不做顺带写入（`last_seen_at`、续期）；查好友码也停 |
  | 停服 | 调用 ≥ 60,000，或 D1 写入合计 ≥ 80,000，或读取 ≥ 450 万行 | `/api/*` 一律 503 `busy`，不碰 D1（计量照常上报，第二天自动恢复）；退出只清 cookie；平台页面照常；开了登录闸门的游戏首页也回 503（fail-closed，15.8），进不去游戏，已打开的局不受影响 |

  - **调用阈值的依据**：2026-10-13 用 GraphQL 查部署账户近 7 天的 Worker 调用数（不含 DO）：全账户每天 231–1,297 次，其中与本项目无关的其他 Worker 合计每天不到 800 次，所以 4 万 / 6 万留足了余量。
  - **为什么停增长档要限制覆盖变大**：只停新建槽的话，有人囤一批号、每个号先建小槽，等库到 300 MB 后让这些号一起把存档覆盖变大，一天内就能把库推到只读档、全站登录注册都停。
  - **存储档位要人处理**：库不会自己变小。到"停增长"就报给维护者：查是谁占的、清理，或开付费版（单库 10 GB）。
  - `GET /api/me` 返回当前档位，平台界面和游戏据此提示"服务器有点忙"（只读档）或暂停云同步（停服档或存档预算用完）。
- **紧急开关**：Secret `API_MODE`（`normal` / `readonly` / `off`，不设按 `normal`；不放 `vars`，免得两处冲突）。值不分大小写、去首尾空白；设了但认不出的值按 `off` 处理（fail-closed）并记日志。
  出事时维护者直接改，不等 PR（要有能部署这个 Worker 的 Cloudflare 凭证，放在环境变量 `CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`）：`cd platform && printf off | npx wrangler secret put API_MODE`（恢复：`printf normal | …`）。
  `wrangler secret put` 用当前线上代码生成新版本立即生效，不用重新构建。改完在 PR 或 issue 里记一笔。**分批发布进行中时 `secret put` 会失败**：先等发布完成，或先 `npx wrangler rollback` 再设。

## 7. 数据（平台 D1）

库名 `arcade`（`primary_location_hint` 为 apac），Worker 里的绑定名 `DB`；库 id 不写在仓库里，部署时由 `production` 环境的 secret 注入。迁移文件放 `platform/migrations/`，编号递增、只增不删，时间一律存 Unix 毫秒整数。
自托管时同一份迁移的 PG 版在 `tools/selfhost/pg/migrations/`，文件名一一对应（3.1）。


迁移：0001 账号、0002 `users.role`、0003 排行榜、0004 设置、0005 钱包、0006 在线位置、0007 邀请、0008 动态、0009 挑战、0010 搭子、0011 邀请码、0012 监控（`monitor_counts`、`meter_hourly.rows_mon`）。设计取舍（都为少写行数）：
- **全部用 `WITHOUT ROWID`**：主键是 TEXT 或多列的普通表，SQLite 会另建一个自动唯一索引、每次插入多算 1 行；`WITHOUT ROWID` 表的主键就是表本身。
- **`credentials` 主键是 `(user_id, type)`，没有 identifier 列和额外索引**：密码和恢复码都是先按用户名找到用户再比对，注册因此从约 13 行降到约 9 行。代价是每种类型只能有一条；以后多个 passkey、第三方登录**另建表**，不改这张表。
- **注销是直接删除**，没有 `deleted_at`，也没有游客。
- **`users.role` 不建索引**：只有管理接口和 Cron 按它查，人数少，全表扫比每次插入多写一行索引划算。
- **`boards` 主键以 `user_id` 开头**：按人删是主键前缀扫描；**排名索引带上 `updated_at`**：同分先达到的在前，也能直接按索引取前 50（`platform/test/boards.test.ts` 在 2,000 人的榜上断言读的行数少于 300）；Cron 删旧的每日榜也沿这个索引按 `board_id` 范围删。
- **一定要先迁移再部署**：新 Worker 上报计量时要写新加的列，没有就上报失败、fail-closed 进停服档。CI 部署前会自动跑迁移（第 8 节）。

### 7.2 每个操作写几行

D1 按写入行数计费：插入时表本身一行，每个索引再各算一行；更新不碰索引列只算 1 行，改了带索引的列算 2 行；**删除即使表带索引也只算 1 行**；删不存在的行 0 行。"类别"是 6.6 的预算类别。
依据：`platform/test/d1-facts.test.ts` 实测（插入 users 3、sessions 2、credentials 1、saves 1、friendships 2）；每个接口的测试都用 `meta.rows_written` 断言下表的值。

**最坏情况**（匿名刷登录，每次换 IP、随机用户名）：每次尝试新建一个 `login:ip` 行（1），日后清理再 1 行（记系统类）。全站每小时 300 次的上限有上报滞后（6.6），按被刷时 30 个 isolate 估（推断），每小时约 600 次，一天约 1.4 万次。
真正封顶的是"登录找回"类预算（9,000 行，加上滞后超出约几百行）；之后登录、找回 503，已登录的玩家照常存档。清理的那一半记系统类（3,500 行），用完 Cron 当天停清，剩下的留到第二天。
各类预算合计 4 万，加上账号安全类最多 3,000 行的超额和各类的滞后，离只读档的 5 万还有约 7,000 行余量；正常情况下一类被刷不会连带全站只读。

### 7.3 注销与清理

- **注销**：再验证后一次 `db.batch`（D1 里是一个事务），删掉这个人在 users、sessions、credentials、saves、boards、friendships（两个方向）、blocks（两个方向）、wallets、invites（发出的、收到的）、feed（本人发的）、feed_reactions（本人赞的；别人给本人动态的赞 7 天后跟着 Cron 删）、
  challenges 和 challenge_results（本人发起的连同所有结果、本人交的结果）、mates（本人在 `lo`、`hi` 两边的）、invite_codes（本人生成的全删；本人注册时用过的那个只清 `used_by`、留 `used_at`，邀请人的额度不还，不然"邀请 → 让对方注销 → 再邀请"能绕过额度）、
  rate_counters（键里带他的用户 id 或用户名的）里的所有行。计数键清单在 `deleteUserStatements`（`worker/api/session.ts`）：`login:fail`、`reauth:fail`、`profile`、`acct`、`save`、`freq`、`fcode`、`fcnew`、`block`、`score`、`admin`、`react`、`chal`。
  管理员删号、一年清理用同一套语句。`blocks` 按被屏蔽方删除没有索引、要扫全表，注销很少，接受。**以后加的表和新的计数键都要加进这个 batch，并有"注销后删干净"的测试。**
- **1 年未登录**：每天的 Cron 找出 `last_seen_at` 早于 365 天前、`role = 'user'` 的用户（没有索引，只花读行数），每次最多 200 个，按注销同样的语句删。**管理员不清**。注意存档接口不更新 `last_seen_at`（5.5）。
- **每天的 Cron 先记筹码统计**（5.9），先于一年清理；出错只记日志，不影响后面的清理。
- **每天的 Cron 还清理**：过期的会话、窗口已过的 `rate_counters`、**60 天前的每日榜**（`dailyBoardKeepDays`，北京时间，带不带 `-v<n>` 都算；固定榜不动；沿排名索引按 `board_id` 范围删，这也是榜单 ID 把日期放在版本号前面的原因，9.2）、
  7 天前的 `meter_hourly` 和 `monitor_counts`、2 天前的邀请、7 天前的动态和赞、30 天前的挑战和结果、过期或撤回满 30 天的没用邀请码。清理的写入算进"系统"类，每次最多删 3,000 行（`cleanupMaxRows`），删不完的留到第二天。
  每一段单独兜住：一段出错只记段名和错误类型，接着清下一段。
- 隐私说明里写明：备份（Time Travel）会在 30 天内自然过期。

### 7.4 房间数据

进行中的牌局状态只放在房间 DO 里，结束后随 `deleteAll()` 删掉，不写 D1（战绩走钱包的 `settle` 小结和 `together()`，5.9、5.10）。排行榜只有 `boards`；没有赛季榜，要做的话先考虑在 `games.ts` 登记一个固定榜复用 `boards`。
**写入要算索引行**（7.2）：新加索引前先算一遍"每次写入多几行 × 每天多少次"。

### 7.5 备份、迁移、容量

- **备份**：D1 Time Travel 付费版可回滚 30 天、免费版 7 天；房间 DO 的 SQLite 也能回滚 30 天。自托管见 `tools/selfhost/README.md` 的 `backup.sh` / `restore.sh`。
- **迁移**：只增不删，先加新字段、再停用旧字段。CI 里先迁移、再发布（第 8 节）。
- **容量**：单库免费 500 MB、付费 10 GB，现阶段远远够用。

## 8. 仓库与发布

- **单一总仓库**：所有模块都在 `yyyu-star/arcade` 里（AGENTS.md 第 0、1 节）。共用的联机代码是 `packages/arcade-kit/`（已发 npm：`@yyyu-star/arcade-kit`），按子路径导出 `room`、`worker`、`game`、`client`、`protocol`、`meter`、`auth` 等；
  游戏和平台在 `package.json` 里写 `"arcade-kit": "file:../../packages/arcade-kit"`，这是 AGENTS.md 允许的唯一跨目录引用。kit 自己也是模块：自带 lockfile、测试和 `pkg-arcade-kit.yml`（只测不部署）。拆成独立仓库时把 `file:` 换成 npm 版本（`tools/split-module.sh`）。
- **改 kit 会触发所有用到它的模块**：每个模块流程的 `paths` 都包含 `packages/arcade-kit/**`，所以改 kit 的 PR 上这些模块的 `test` 都会跑，合并后都会重新部署（安全修复要的就是这个效果）。kit 的接口改动要么兼容，要么同一批里把用到的模块都改好；
  按"一个 PR 只改一个模块"，kit 和使用方分 PR，kit 先保持兼容再合并；改 kit 后每个游戏跑 `npm test` 加 `npm run test:room`。游戏用到哪个 kit 版本以各自 `package.json` 为准（自托管 PG 房间模式要 ≥ 0.21）。
- **发布顺序**：D1 迁移 → 平台 → 游戏。跨模块的改动拆成几个 PR，在描述里写明顺序，前一个合并并部署后再合并下一个。部署由维护者在 `production` 环境批准，不同模块可同时发（AGENTS.md 第 5 节、`CONTRIBUTING.md`）。
- **不另建测试环境**：正式环境只有平台 `arcade` 加每个游戏各一个 Worker，**不建任何测试或实验 Worker**（没有 staging、第二套 D1 和 Secret）。每多一个 Worker 就多一套路由、绑定、Secret 和凭证要管。
  验证靠：**本地**（vitest + `@cloudflare/vitest-plugin`，本地 D1、DO 在 miniflare 里跑；`wrangler dev --local` 联调）→ **PR 上的 CI**（`test` 作业跑单元和集成测试、构建、冒烟、`check-isolation`；不往线上部署功能分支，也不用预览链接测账号）→ **合并后暗上线**（接口先上线，入口藏在构建期常量或服务端开关后面，在正式站点验证过再打开）。
  代价（要认）：暗上线发生在正式账户上，有 bug 的接口也会占正式额度，所以接口要先过本地的写入行数断言，新入口先关着。出事靠 6.6 的计量熔断和 `API_MODE`；功能有问题默认往前修（AGENTS.md 第 5 节）；D1 迁移只增不删，所以回退代码不用回退库。
- **测试**：规则是纯函数，用 vitest 测；房间用 `@cloudflare/vitest-plugin` 做集成测试（带 WebSocket 时用 `--no-isolate`）；kit 断言写入预算和硬限制；
  **平台接口**：测试前把 `platform/migrations/` 应用到本地 D1，每个接口测正常路径、`meta.rows_written` 等于 7.2 的值、缺 `X-Arcade` 或 `Origin` 不对 403、超限 429、存档 409、注销后各表删干净；
  **平台界面冒烟** `npm run smoke`（`platform/tools/smoke.ts`）：用临时目录里的本地 D1 和假 Secret 起 `wrangler dev`（端口 5181，被占用就失败），无头 Chromium 走完主流程，控制台零报错、CSP 不拦任何东西、所有 4xx/5xx 要事先声明；不需要 Cloudflare 凭证，本地约 60–90 秒，CI 的 `test` 作业会跑。
- **部署流程**：`.github/workflows/platform.yml` 等是仓库根文件。PR 上 `test` 作业跑 `npm test`、构建、冒烟；main 上 deploy 作业经批准后用 `tools/deployer/deploy.mjs` 部署，部署前先 `wrangler d1 migrations apply`，迁移失败就不部署。
  Secret（`PEPPER_PW`、`PEPPER_RC`、`PEPPER_SID`、`PEPPER_IP`、`ADMIN_TOKEN`，值写成 `<kid>:<随机串>`，`platform/.dev.vars.example`）由维护者 `wrangler secret put` 设一次，不进 Git、不进 workflow，另在仓库外安全地存一份备份（Worker 被删又没有备份，所有密码和恢复码都会失效）。
  站点主机名和 D1 的 `database_id` 由 `production` 环境的 secret（`SITE_HOST`、`D1_DATABASE_ID`）注入，不写进仓库。`API_MODE` 是 Secret，不写进 `vars`（6.6）。
- **观测**：Workers Logs 平时关着，查问题用 `wrangler tail`（5.2）。

## 9. 联机形态

两个游戏的玩法差别很大，联机形态也不一样：掼蛋这类牌桌游戏是多人轮流出牌、有隐藏信息，必须实时同场；开盘是一个人对着行情做决策，同场实时没有意义，比的是同一局谁赚得多。

### 9.1 牌桌游戏：好友房实时联机

掼蛋、德州、麻将、飞驰都按 4.x 的规范接 kit（各游戏的细节以 `games/<id>/AGENTS.md`、`DESIGN.md` 和 `packages/arcade-kit/README.md` 为准）。以掼蛋为例：

- 好友用 6 位房间码开房进房：开房 `POST /games/guandan/room/rooms`，进房 WebSocket `/games/guandan/room/rooms/<房间码>/ws?cv=<客户端版本>`（版本太旧回 4005，叫人刷新）；服务端开关 `ONLINE`（`wrangler.jsonc` 的 vars，`on` 才收开房）。
  标题页一直有"好友房"，`?online=1` 启动后直接打开好友房面板（平台大厅入口用），`room=<码>` 直接进房（邀请链接）。浏览器记着上一次的房间（`guandan.room`，带账号 id），标题页给"回到房间"。
- 房间限额按游戏调过：掼蛋一生入站 8,000 条、寿命 8 小时、电脑一次最多连出 3 步（4.6）。结算页每个真人点"继续"或 20 秒到了由房间发下一副。
- **补位**：开房时空座位默认坐电脑，1 个真人也能开局；**只有房主能开局**（别人发 `start` 回 `not_host`）；好友进房时选一个电脑座位接管。开打后坐过的人只能回自己的座位，没坐过的人只能接管没绑人的电脑座位。
  另有快速匹配（4.6，设计在 `packages/arcade-kit/docs/match.md`）。
- **一眼分清**：电脑头像带"电脑"角标和固定的头像框（角标形状不同，不只靠颜色）；真人昵称不许用电脑人物的名字（5.1、第 10 节）。电脑的性格只影响台词和表情，不影响出牌。
- **口头禅、出牌台词**由每个浏览器根据房间下发的牌局事件**自己播放**，不发消息，不占 4.6 的消息预算；快捷短语、聊天、表情道具的限速在房间里（`emoteMs`、`chatMs` 等，kit README），被屏蔽的人的表情和聊天自己看不到。
- **规则核心要求**（纯函数，浏览器和房间共用）：超时代出 `timeoutAction`（只看该座位能看到的信息，"能不出就不出、必须出就出最小合法牌"）；`nextDeal` 由房间发出；结算页要展示的下一副信息由服务端算好随结算下发；
  状态里记**规则版本**；**种子只在服务端生成**（`crypto.getRandomValues`）。画面层的视角旋转（服务端按真实座位号发，客户端统一转成"我 = 0"）必须有单元测试覆盖转 0–3 格。
- 文字一律大白话，不嘲弄人，不拿伤亡开玩笑（AGENTS.md 第 4 节）。

### 9.2 开盘：每日挑战排行（简单版，不防作弊）

**不做实时同场**，用排行榜就够了。**不防作弊**：能作弊算玩家自己的本事。所以排行榜做成简单版（代码 `platform/worker/api/boards.ts`）：

- **游戏直接交分**：游戏页调同域的 `POST /api/scores {gameId, boardId, score, userId?}`，不经过游戏 Worker。
- **平台只管两件事**：防刷额度、查数据合法性（类型、范围、频率、体积）。不存操作记录，不重放，没有成绩票，不判"分数合不合理"，也不限"每天只认首次"。
- **所以不需要付费版**：原设计要服务端重放验分，实验 E5 证明可行但 CPU 超免费版 10 ms（Worker 里 p50 14.5 ms、p99 46.6 ms），后来整个取消（成绩票、`board_runs`、操作记录都不做）。好友同局挑战靠 15.18 的异步挑战，不重算。

**规则**（数字以 `config.ts` 为准）：

- **每人每榜只留最好的一条，越高越好**。越低越好的游戏交相反数。用一条带条件的 UPSERT 实现，并发交不同的分也留最高的。
- **榜单 ID 只收两种形式**，别的一律 422 `invalid_board`，免得随便开榜把库撑大：
  - **每日榜** `daily-YYYY-MM-DD`，规则大改时在后面加版本号 `-v<n>`（n 为 1–99）。日期用**北京时间**，交分时只收北京时间的昨天、今天、明天。有子榜的游戏是 `daily-YYYY-MM-DD-<子榜>[-v<n>]`（15.5）。
  - **固定榜**（不按日期，如 `endless`）：要先在 `platform/src/games.ts` 里给这个游戏登记 `boards`（名字 `[a-z0-9-]{1,40}`，不以 `daily` 开头）。
  - **日期放在版本号前面**：同一个游戏的每日榜按 `board_id` 排序就是按日期排，Cron 可以沿索引按范围删旧榜。
- **分数**：安全整数，|score| ≤ 1e12，否则 422 `invalid_score`；类型不对 400。
- **频率**：每人每天最多交 200 次（所有游戏、所有榜合计，没刷新纪录的也算），超了 429。写入记在"排行榜"类预算（6.6）：刷榜只停交分，不把云存档挤停。
- **体积**：每人每榜一行；每日榜 60 天后由 Cron 删，固定榜不删；停增长档停交分。
- **读榜**：`GET /api/boards/<gameId>/<boardId>?scope=all|friends`，前 50 名和我的名次；只给昵称、头像、分数，不给用户名和 userId；好友榜只算我和已接受的好友（15.5）。

**给游戏的提醒**（游戏自己处理，平台不管）：
- **种子由游戏自己推导**（比如由游戏 id 和北京日期推出当天的种子），平台不发种子。
- **行情段要固定**：真实行情段按种子哈希取余选，段库加了新段，同一个种子会选到别的段；每日挑战的选段方法要跟着版本走，规则或段库大改时换 `-v<n>`。
- **回落到合成行情的一局**（真实行情下载失败时）和别人不是同一局，不交分或提示"这局不计入排行"。
- **什么时候交分**：一局结束出结算画面时交一次，不要每一步都交（每人每天 200 次，几个游戏共用）；各种返回码怎么处理见 15.5。
- 懂行的人能提前看到后面的走势、能改分数——这些都不管。

## 10. 合规底线

- **不碰真钱**：积分、筹码只能拿来玩，不能买、不能兑换、不能转让或赠送；不设现金或实物奖品；界面上写明"无任何现金价值"；每日挑战排行只是当天的名次，没有奖励。
- **个人信息**：不登录不收集任何信息；注册只要用户名、密码和昵称，不收手机号、邮箱；有隐私说明，可以注销账号并删除数据；IP 只存带密钥的哈希（HMAC），因为普通哈希可以被暴力还原。
- **昵称和聊天**：昵称过敏感词，并且不许用各游戏电脑人物的名字，免得真人冒充电脑；可以屏蔽。联机房间的聊天和快捷语见 kit 的 `docs/chat.md`（有限速、打码词和屏蔽）。
- **防沉迷、版号、ICP**：这些规定针对国内持证运营的网络游戏。我们是免费、无充值、境外托管的小站，处在灰色边缘，规模一大风险就上升。微信可能对没有 ICP 备案的域名弹出拦截提示，影响分享房间链接。做大或商业化之前要咨询专业意见。这一条是调研结论，不是法律意见。

## 11. 研究实验（已结束）

2026-10-14 起实验阶段结束，实验用的临时 Worker 和域名都已删除，今后也不再建（第 8 节）。结论：

| 实验 | 结论 |
|---|---|
| E1 WebSocket 经自定义域名 + 路径路由 | **通过**。路径路由优先于自定义域名；浏览器导航式请求进了 Worker，没被单页回退吞成 HTML；5 桌 × 4 人 10 分钟，握手 20/20、0 断线，走子往返 p50 84 / p99 106 ms（测试网络经香港，不代表大陆网络） |
| E2 国内真实延迟、各运营商 | **不再单独做**。只有一次家用 WiFi 实测 p99 86 ms（经代理，不代表普通国内网络）；各运营商、4G 的延迟在真实游戏上看。牌类可以接受 200–300 ms |
| E3 微信、QQ 内置浏览器打开和切后台续连 | 后移到真实游戏上看；被拦就改用"复制房间码" |
| E4 断线续局 | 服务端断开：修了续局写法（4.5）后**通过**，6 次断开、48 次重连全部续上，重连 p50 约 0.6–1 秒；部署：不断线、步序全对，但新旧代码会并存几分钟（协议要新旧兼容）；飞行模式待真机测 |
| E5 开盘重放 CPU | 免费版**不够**（p50 14.5 ms、p99 46.6 ms），因此排行榜改成简单版、不重放（9.2） |

## 15. 接口约定（`/api/*`）

> 给平台和游戏的开发者参考。接口**只增不改**（`platform/AGENTS.md`）：已上线的字段不改含义、不删除，新能力加新字段或新路径，所以路径里不带版本号。不存在的路径返回 404 `not_found`。
> 写入行数的来历见 7.2，限流见 15.6。括号里的版本号是该接口所在的平台版本。

### 15.1 通用规则

- **格式**：请求和响应都是 JSON（`content-type: application/json`），UTF-8；字段名 camelCase；时间是 Unix 毫秒整数。
- **身份**：凭 cookie `__Host-sid`（5.1）。唯一的例外是 `/api/admin/*` 可以用 `Authorization: Bearer <ADMIN_TOKEN>`（5.8、15.7），别的接口不认 `Authorization` 头。
- **只认站点主机名**：请求的 Host 必须是 `SITE_ORIGIN` 的主机名，否则 404 `not_found`。
- **写请求**（POST、PUT、PATCH、DELETE）必须带 `X-Arcade: 1`，且 `Origin` 等于站点地址（浏览器同域 `fetch` 自动带）。不开 CORS，`OPTIONS` 返回 405。这只挡浏览器里的跨站请求（5.2）。
- **请求体上限**：默认 8 KB；`PUT /api/saves/…` 为 52 KB（48 KB 数据加外层，在 keepalive 的 64 KB 之内）。先看 `content-length`，没有时边读边数，超了立即 413。整个请求体嵌套最多 64 层，超了 400 `bad_request`（解析前数括号）。
- **响应头**：所有 `/api` 响应带 `cache-control: no-store`。
- **检查顺序**（便宜的在前，5.4；按 `platform/worker/api/router.ts` 的实际顺序）：
  1. Host → 404；方法和路径白名单 → 404 / 405；
  2. 熔断档位、停增长档要停的接口和这个接口所属类别的写入预算（内存里，6.6）→ 503 `busy`（退出在任何档位都照做）；
  3. 写请求的 `X-Arcade`、`Origin` → 403 `forbidden`；
  4. 路径参数（`gameId` 白名单 404 `unknown_game`、槽名 422 `invalid_slot`、榜单 ID / 好友码 / 用户 id 格式 404 `not_found`），在读请求体和会话之前校验，不碰 D1；
  5. 请求体大小 → 413；JSON 解析和嵌套层数 → 400；
  6. 读会话（D1 读）→ 要登录的接口 401 `unauthorized`；
  7. 接口内部依次：预期账号 `userId`（格式不对 400，和会话不一致 409 `wrong_user`）→ 其余字段的类型和内容（400 / 404 / 422）→ isolate 内存限流 → 持久限流计数（超限 0 行写入，429）→ 业务。

  所以没登录或会话失效时，哪怕请求体字段格式不对，回的也是 401（匿名接口不读会话）。第 2 步的 503 先于 `wrong_user`，每天次数用完的 429 在 `wrong_user` 之后；存档在停增长档的 503 是接口内部判断的，排在 `wrong_user` 之后，交分的停增长档在第 2 步。
- **错误响应**：`{"error": "<错误码>", "message": "<给玩家看的中文>"}`；429 另带 `retryAfter`（秒）和 `Retry-After` 头。调用方按 `error` 判断，`message` 只拿来显示。

| HTTP | `error` | 什么时候 |
|---|---|---|
| 400 | `bad_request` | 不是 JSON、缺字段、类型不对；预期账号 `userId` 格式不对；读榜的 `scope` 不对 |
| 400 | `bad_amount` | 管理员加减筹码的数不是非零整数，或超过单次上限（响应带 `max`） |
| 400 | `invite_invalid` | 邀请码不对、已用、过期或撤回（不说是哪种；只写了试码计数 1 行） |
| 401 | `unauthorized` | 要登录但没登录，或会话已失效（同时清掉两个 cookie）；管理接口的 Bearer 令牌不对 |
| 401 | `bad_credentials` | 用户名、密码或恢复码不对（不说是哪个不对） |
| 403 | `forbidden` | 写请求缺 `X-Arcade: 1` 或 `Origin` 不对 |
| 403 | `registration_closed` | 注册已关闭且没带邀请码（写 0 行） |
| 403 | `not_admin` / `admin_protected` | 管理接口，登录了但不是管理员 / 会话管理员动管理员账号或建管理员 |
| 403 | `not_friend` | 邀请：不是好友、屏蔽了、对方不存在、叫自己，一律这个 |
| 404 | `not_found` | 没有这个接口，或要找的对象不存在（好友码、好友请求、屏蔽对象、不认识的榜） |
| 404 | `unknown_game` | `gameId` 不在平台的游戏白名单里 |
| 405 | `method_not_allowed` | 路径对、方法不对 |
| 409 | `username_taken` / `invite_used` / `quota_full` | 用户名已占用 / 邀请码被别人先用了 / 邀请名额用完（带 `quota`） |
| 409 | `conflict` | 存档版本冲突，响应里带 `current` |
| 409 | `wrong_user` | 带的预期账号和会话不一致，"账号换过了，刷新一下页面"；不带 `current`，写 0 行 |
| 409 | `cannot_delete_self` / `last_admin` | 会话管理员删自己 / 删最后一个管理员 |
| 409 | `relief_used` / `relief_not_needed` / `no_change` | 领补给：今天领过了 / 筹码还够用；管理员加减筹码什么也没变（带 `wallet`） |
| 409 | `full` | 挑战已有 100 个人交了 |
| 413 | `too_large` / `quota_exceeded` | 请求体或单个存档槽超限 / 存档每人合计 256 KB 或每个游戏 8 个槽超了 |
| 422 | `invalid_username`、`weak_password`、`invalid_display_name`、`reserved_display_name`、`invalid_slot`、`invalid_target` | 字段格式对但内容不合规 |
| 422 | `limit_reached` / `unblock_first` | 待处理好友请求或好友数到上限 / 想加的人是自己屏蔽了的 |
| 422 | `invalid_board`、`invalid_score` | 交分的榜单 ID 不收，或分数不是安全整数、超过 ±1e12 |
| 429 | `rate_limited` / `too_soon` | 超了限流，带 `retryAfter` / 同一个存档槽 10 秒内重复写 |
| 500 | `internal` | 服务端出错（日志里记接口和错误码，不记请求体） |
| 503 | `busy` | 这一类的写入预算用完、停增长档的注册 / 交分 / 新建存档槽 / 存档覆盖变大、只读档的写接口（和查好友码），或停服档的所有接口（6.6） |
| 503 | `unavailable` | D1 一时出错或读不到全站计量；带 `retryAfter`（2、5 或 10 秒）。和 `busy` 不同，过几秒就好 |

- **401 清 cookie**：只要请求带着 `__Host-sid` 却没有有效会话（改了密码、退出其他设备、过期），**所有要登录的接口**的 401 都附上两个清 cookie 的 `Set-Cookie`。没带 `__Host-sid` 的 401 不发。
- **客户端约定**：返回的不是 JSON（Cloudflare 或网关的出错页）按"连不上"处理，断网同理；**只有接口明确回了 `error: "busy"` 才算停服**（`unavailable` 按"连不上、过几秒再试"）。连不上时不要放登录入口、也不要叫人去登录（5.7）。

**用户对象**（下文的 `user`）：`{"id", "username", "displayName", "friendCode", "avatar": null, "catchphraseId": null, "createdAt"}`，管理员多 `"isAdmin": true`，`showWhere` / `showFeed` / `showMates` 三个开关。
只返回给本人；给别人看的是**公开资料** `{"userId", "displayName", "avatar"}`，不含用户名（5.6）。下文"谁能调"里的"平台页"是**界面约定**，服务端拦不住游戏页调用（5.2）。

### 15.3 云存档

| 接口 | 谁能调 | 请求 | 成功 | 主要错误 | 写入 |
|---|---|---|---|---|---|
| `GET /api/saves/<gameId>[?userId=<id>]` | 登录；游戏页可调 | `userId` 可选 | 200 `{"saves": [{"slot", "rev", "updatedAt", "data"}]}`（没有存档时是空数组） | 401；404 `unknown_game`；400（`userId` 格式不对）；409 `wrong_user` | 0 |
| `PUT /api/saves/<gameId>/<slot>` | 登录；游戏页可调（含 `fetch keepalive`） | `{"baseRev": 0 或当前 rev, "data": 任意 JSON, "userId"?: 预期账号}` | 200 `{"rev": 新 rev, "updatedAt"}` | 409 `conflict` / `wrong_user`；400；413 `too_large` / `quota_exceeded`；422 `invalid_slot`；429 `too_soon` / `rate_limited`；404；503 `busy`（停增长档） | 成功 2；409、`too_soon`、`quota_exceeded`、停增长档覆盖变大为 1（只有 `save:<userId>` 计数）；格式错、`wrong_user`、`too_large`、`rate_limited`、停增长档新建槽为 0 |

- `baseRev` 为 0 表示新建；云端已有这个槽时也按冲突处理（停增长档例外：直接 503）。冲突响应 `{"error": "conflict", "current": {"rev", "updatedAt", "data"}}`，游戏合并后用 `current.rev` 重交；`baseRev` 大于 0 但云端没有这个槽时 `current` 为 `null`，游戏改用 `baseRev` 0 重交。
  `rev` 从 1 开始，每次成功加 1。`data` 按序列化后的 UTF-8 字节数算，≤ 48 KB。429 `too_soon` 带 `retryAfter` 和 `Retry-After`。
- **判断顺序**（一条 SQL 没写进去时再读一次判断）：版本不对 409 → 10 秒内 `too_soon` → 停增长档覆盖变大 503 → `quota_exceeded`。`GET` 不做 `last_seen_at` 写入，所以游戏要另外调 `/api/me`（5.5）。
  没有按单个槽读的 GET，也没有删除单个槽的接口（注销会删光）。

**预期账号 `userId`**（为什么要它见 5.5）：
- **可选**，不带就和以前一样，老游戏不用改。值填 `/api/me` 返回的 `user.id`。`PUT` 只认请求体里的 `userId`；`GET` 只认查询参数 `?userId=`。
- **和会话不一致**：409 `wrong_user`，在接口的第一步判断，**写 0 行、读 0 行（不读存档表），不计数，也不返回任何存档数据**。
- **格式不对**：400。合格的是 1–64 个 `[A-Za-z0-9_-]` 的字符串。GET 另有几种也算格式不对：带了多个 `userId`、`?userId` 没有等号或值为空、参数名大小写不同（`userid`、`UserId`，解码后比较），免得游戏端拼错了被悄悄当成"没带"。
- **没登录或会话失效**：路由的登录检查在前，一律 401。只读档下读存档照常，带了 `userId` 也照常判断。
- **409 有两种，必须按 `error` 区分**：`conflict`（同账号版本冲突，带 `current`，合并后重交）和 `wrong_user`（**没有 `current`**，不合并、不重试，按"换了账号"处理）。把 `wrong_user` 当成 `conflict` 去合并，就正好把账号串了。

### 15.5 排行榜

简单版，不防作弊（9.2）。代码 `platform/worker/api/boards.ts`，写入记"排行榜"类预算（6.6）。

| 接口 | 谁能调 | 请求 | 成功 | 主要错误 | 写入 |
|---|---|---|---|---|---|
| `POST /api/scores` | 登录；游戏页可调 | `{"gameId", "boardId", "score", "userId"?}` | 200 `{"best": 最好成绩, "improved": true}`（新纪录）或 `{"best": 原来的, "improved": false}`（没比原来好，含相等） | 400；404 `unknown_game`；409 `wrong_user`；422 `invalid_board` / `invalid_score`；429（每天 200 次）；503 `busy` | 新上榜或刷新纪录 3；没更好 1；各种被拒 0 |
| `GET /api/boards/<gameId>/<boardId>?scope=all\|friends` | 登录；游戏页可调 | `scope` 默认 `all` | 200 `{"entries": [{"rank", "displayName", "avatar", "score", "isMe"}], "me": {"rank", "score"} 或 null}` | 400（`scope` 不对）；401；404 `unknown_game` / `not_found` | 0 |

- **榜单 ID**：每日榜 `daily-YYYY-MM-DD[-v<n>]`，日期必须是北京时间的昨天、今天或明天；一天几个每日榜的游戏（`games.ts` 的 `daily` 写了子榜）是 `daily-YYYY-MM-DD-<子榜>[-v<n>]`，子榜要登记过（`[a-z][a-z0-9]{0,15}`，不能像版本号 `v2`），
  写了子榜的游戏不再收不带子榜的每日榜，没写子榜的游戏不收带子榜的；固定榜要在 `games.ts` 该游戏的 `boards` 里登记。读榜时每日榜不限日期（过期还没删的照样能读），固定榜同样要登记过。
- **分数**：安全整数，|score| ≤ 1e12；越高越好，越低越好的游戏交相反数。**每天 200 次**：`score:<userId>`，所有游戏、所有榜合计，没刷新纪录的也算，超了 429、写 0 行。
- **预期账号 `userId`**：规则同 PUT 存档，只认请求体：不一致 409 `wrong_user`，在计数之前判断；格式不对 400。读榜不带 `userId`（读到的只拿来显示，用错账号读一次也不会串号）。
- **读榜返回**：`entries` 是前 50 名，同分同名次（1、1、3），同分时先达到的排前面；只给昵称、头像、分数，**不给用户名，也不给 userId**。`me` 是我的名次和分数，不在前 50 也给，没交过分时是 null；
  全站范围里比我高的人最多数到 1 万个（`boardRankCountMax`），再多时 `me.rank` 是 null，界面显示"1 万名以后"。我和第 50 名同分但达到得比他晚时，`me.rank` ≤ 50 而 `entries` 里没有我，界面在榜单下面单独显示一行"我：第 X 名"。
  `friends` 范围只算我和已接受的好友。读的行数和榜的大小无关（好友榜从好友名单出发按主键逐个查，`CROSS JOIN` 固定连接顺序）。
- **给游戏的约定**：一局结束出结算画面时交一次，不要每一步都交；200 显示"新纪录"或"最好成绩 X"；429 提示"今天的成绩先记到这里"，不重试；503 `busy` 提示"排行榜暂停，稍后再来"，不重试；
  409 `wrong_user` 提示刷新页面，不重试；连不上提示"没连上，成绩没记上"，可以给"重试"按钮，不自动循环；401 是没登录（登录闸门会先挡住）；422 或 404 是游戏代码的错，开发时修掉。不需要游戏 Worker 参与，浏览器直接调同域 `/api`。

### 15.6 限流总表

键里的 `<ip>` 是 5.1 的 IP 哈希；"天"按 UTC 算。持久计数一律用带条件的 UPSERT：**超限被拒的请求写 0 行**；每新建一行，日后清理再算 1 行（5.4、7.2）。数字以 `config.ts` 为准。

| 键 | 窗口 | 上限 | 超了 | 每次写 |
|---|---|---|---|---|
| isolate 内存令牌桶 | 1 分钟 | 每个 IP 的匿名接口 10 次；注册先过它再读开关 | 429，不碰 D1 | 0 |
| 浏览器报错（另一个内存令牌桶） | 1 分钟 / 5 分钟 | 每个 IP 10 条；同一签名每个 isolate 5 分钟记 1 次（第 16 节） | 429 / 静默 204 | 0 |
| `reg:ip:<ip>` / `reg:all` | 天 | 20 次注册尝试（通过格式检查的才算）/ 300 | 429 | 1 |
| `login:ip:<ip>` | 1 小时 | 30 次尝试（成败都算） | 429 | 1 |
| 登录全站（随计量上报） | 1 小时 | 300 次，只算用户名存在的 | 429 | 0 |
| `login:fail:<username>` | 24 小时 | 只在用户名存在时记，算密码之前先占一次（对了清零，锁着时 0 行、429）；连续失败 5 次后，每次等 30 秒 × 2^(失败数 − 5)，最长 1 小时；登录成功或找回成功清零 | 429 | 失败 1（锁着时 0）；清零 1 |

| `inv:ip:<ip>` | 1 小时 | 10 次试邀请码（成败都算）；不设全站上限（15.20） | 429 | 1 |
| `reauth:fail:<userId>` | 24 小时 | 再验证的密码错误，规则同 `login:fail` | 429 | 失败 1（锁着时 0）；成功清零 1 |

| `freq:<userId>` | 天 | 发 30 个好友请求（撤回、被拒都不退还；重复发、已是好友不计） | 429 | 1 |

### 15.8 游戏登录闸门的调用约定

游戏要登录才能进。游戏 Worker 只在**首页的导航请求**上，通过服务绑定 `ARCADE` → `arcade` 问平台"这个人登录了没有"（`worker/gate.ts` 是掼蛋的实现，kit 提供 `loginGate`）：

```ts
const res = await env.ARCADE.fetch('https://<站点>/api/me', {   // 主机名就是 SITE_ORIGIN 的主机名
  headers: { cookie: request.headers.get('cookie') ?? '', 'cf-connecting-ip': request.headers.get('cf-connecting-ip') ?? '' },
});
```

- **判定**：200 且 `body.user` 不为 `null` → 放行；200 且 `user` 为 `null` → 302 到 `/login?from=<游戏id>`（要带着查询回来，比如房间码，用 `/login?next=<encodeURIComponent(路径 + 查询)>`，5.7）；
  其他状态码、不是 JSON、超过 3 秒、绑定不存在 → 回 503 页（**fail-closed**，宁可暂时谁都进不去，也不放行没受邀的人）。
- **只拦首页三个路径**：`/games/<id>`、`/games/<id>/`、`/games/<id>/index.html`（`wrangler.jsonc` 的 `assets.run_worker_first`）。js、图片等资源不经过 Worker。
- **只转发两个头**：整串 `Cookie`（平台只读 `__Host-sid`）和 `cf-connecting-ip`。不用带 `Origin` 和 `X-Arcade`（GET 不检查）。地址的主机名必须是站点主机名，别的写法回 404。
- 平台 `/api/me` 续期或清失效会话时下发的 `Set-Cookie`，闸门在放行和跳登录时原样带回浏览器，平台不可用（503）时不带；否则只玩游戏、不回平台页的人 cookie 到期不续。
- 平台停服（`API_MODE=off` 或计量到停服档）时回 503，游戏应回 503 页；只读档回 200，玩家照常放行。每次闸门检查算平台的 1 次调用；没带 cookie 时不碰 D1。
- 游戏侧开关 `GATE`：`off` 以外的任何值（包括没配）都按 `login` 处理，配错时同样不放行；本站部署时由 `deploy.mjs` 注入 `GATE: "login"`（AGENTS.md 第 2 节）。
- **联机房间进房也走这个约定**（`acceptJoin` / `acceptCreate`，5.3）：同样只转发两个头、3 秒超时、fail-closed，但把"平台不可用"和"没登录"分开报（进房 1013 / 4401，开房 503 / 401）。每次进房算平台 1 次调用。
- **同一个绑定上的 RPC**：平台的默认入口是 `WorkerEntrypoint`，`ARCADE` 绑定除了 `fetch` 还能调 `blockedAmong(userIds)`（好友房聊天用，`packages/arcade-kit/docs/chat.md`）：
  回这几个人之间的屏蔽关系 `[[屏蔽的人, 被屏蔽的人], …]`。`userIds` 去重、不像用户编号的忽略，最多 9 个（超过回 `[]`、不查）；只读，一条查询，一行不写；停服或出错回 `[]`、不抛异常，房间退回只用本地屏蔽。
  `/api` 里没有这条路（浏览器拿到了就能试出谁屏蔽了自己）。旧平台、单独部署的游戏没有这个方法，游戏要当它可能不存在。
  入口改成类以后 RPC 能调到原型上的每个公开方法，所以定时清理 `scheduled` 写成实例字段（RPC 只认原型上的方法，cron 照常找得到它），经 RPC 只露出 `fetch` 和 `blockedAmong`，测试锁住了原型上的方法名（`platform/test/blocked-among.test.ts`）。

### 15.10 错误码给玩家怎么说

原则：玩家正常玩不该碰到限制；万一碰到，给一句大白话，说清楚出了什么事、怎么办，不只回一个错误码。平台页面照这张表显示（`/api` 回包里的 `message` 就是"给玩家看"这一列）；游戏收到钱包 RPC 的错误码时可以按游戏的语气改字，但"怎么办"要留着。

**钱包 RPC（游戏收到，5.9）**

| 错误码 | 什么时候 | 给玩家看 | 游戏怎么做 |
|---|---|---|---|
| `no_funds` | 余额不够这次带入 | 钱包里的筹码不够，少带一点，或者去大厅领补给 | 给"少带一点"的选项和去 `/wallet` 的链接 |
| `limit` | 今天带入、领补给合计满 1,000 次 | 今天开局太多了，明早 0 点恢复；桌上的照常结回 | 娱乐模式照常能玩 |
| `at_table` | 同一个 `ref` 补码换了档 | 这一桌带的是别的档，换一桌再开 | 一般是游戏写错了，记日志 |
| `expired` | 这一份放了超过 24 小时，已经原样退回 | 这一份放太久了，已经原样退回钱包 | 不用再结回 |
| `no_stake` | 结回、放弃时那一份不在（多半已经结过） | 这一份已经结过了 | 刷新钱包显示 |
| `busy` | 档位或钱包预算停了带入、并发冲突 | 服务器今天有点忙，先不能带筹码开局；娱乐局照常玩，明早恢复 | 结回、放弃收到 `busy` 时隔几秒静默重试（只有停服档会拒结回） |
| `bad_request` / `bad_amount` / `bad_until` / `bad_mode` / `bad_game` / `unknown_game` / `no_user` / `op_conflict` | 参数不对（程序写错；`op_conflict` 是同一个 `op` 用来做了两件事） | 出了点问题，这一份筹码没动，刷新一下再试 | 记日志，不重试 |
| `internal` | 平台出错 | 出了点问题，筹码没动，过一会儿再试 | 结回隔几秒用**同一个 `op`** 重试一次 |
| 成功但带 `capped` | 单机实盘今天这个游戏净赢到顶 | 今天单机实盘赢够了，多出的 N 没进钱包；好友房不限 | 照常显示结果，把 N 写出来 |
| 成功但带 `statsIgnored` | 战绩小结不合格（5.10） | 不给玩家看 | 测试里修 |

**`/api`（平台页面和游戏都可能收到）**

| 错误码 | 什么时候 | 给玩家看 |
|---|---|---|
| `rate_limited`（429，带 `retryAfter` 秒） | 各种每人、每 IP 的次数（15.6） | 操作太频繁了，歇一会儿再试（N 分钟后） |
| `too_soon`（429） | 同一个存档槽 10 秒内又存 | 游戏静默稍后再存，不提示 |
| `quota_exceeded`（413） | 云存档空间、槽数满了 | 云存档空间满了，删掉不用的存档再试 |
| `busy`（503） | 全站到了只读档、某一类预算用完 | 服务器今天有点忙，先只能看、不能改，明早恢复 |
| `unavailable`（503，带 `retryAfter` 秒） | D1 一时出错、读不到全站计量 | 服务器一时连不上数据库，过几秒再试 |
| `relief_used` / `relief_not_needed`（409） | 补给今天领过了 / 钱包加桌上的还够补给额 | 今天的补给已经领过了，明早 0 点再来 / 筹码还够用：钱包加桌上的不到补给额才能领 |
| `limit_reached`（422） | 好友 200 个、待处理请求 20 个满了 | 好友或待处理的请求到上限了，先处理掉一些再加 |

### 15.12 排行榜页

`/boards`：本周净赢（总榜 + 每个游戏）、各游戏的每日挑战、各游戏总榜、称号收集，每个都能切"全部 / 只看好友"，点名字进战绩页；电脑上（≥960）左边竖排的榜单分组、右边是榜，手机上标签横着滑。大厅顶栏有"排行"入口。
本周净赢和称号都从钱包行里的 `career` 汇总，**不新增写入**；比的是这周带筹码的局赢了多少，不比总余额（`economy.md` 第 5 节）。记"排行榜"类（只读）。

| 接口 | 请求 | 成功 | 主要错误 | 写入 |
|---|---|---|---|---|
| `GET /api/leaderboard?scope=all\|friends` | 要登录 | 200 `{"week", "scope", "boards": {"total" \| "<game>" \| "titles": {"entries": [{"rank", "userId", "displayName", "avatar", "value", "isMe"}], "me": {"rank", "value"} \| null}}, "daily": {"<game>" \| "<game>:<子榜>": "<今天的每日榜 id>" \| null}}`；每榜前 50，同分同名次；本周榜只算这周结回过的人，称号榜只算拿过称号的人 | 400；401 | 0 |

- **读多少**：全站汇总每个 isolate 缓存 5 分钟（换周、换日立即重算）。缓存过期时读一遍 wallets 加 users，并按 `boards_rank` 索引的前缀查出登记了每日榜的各游戏今天的榜 id。只看好友时另外读我的好友关系，在缓存里筛。
- **每日挑战**由 `games.ts` 的 `daily` 登记驱动：`daily: true` 排行榜页多一个"<游戏名>每日"标签；一天有几个每日榜的，`daily` 写子榜列表 `[{"id": "vigil", "name": "守夜"}, …]`，每个子榜一个标签。
  读榜用 `GET /api/boards/<game>/<每日榜 id>`；每日榜 id 带规则版本，平台不知道游戏现在是第几版，所以取今天已有的榜里版本号最大的。
- **分数怎么显示由游戏给**：游戏在自己的模块里放 `/games/<id>/daily.json`（每日榜）和 `/games/<id>/boards.json`（固定榜，格式相同，按榜 id 分开写在 `boards` 下），平台在浏览器里读（文件最多 32 KB）：
  `{"note": "每天一样的行情，比谁打得好。", "score": [{"from": 100000000000, "text": "通关 · {n} 元"}, {"text": "撑了 {n} 个月"}]}`。`score` 从上往下取第一条能用的：没写 `from` 的总能用，写了的要分数 ≥ `from`；
  `{n}` 是分数减去 `from`，按千分位写；`text` 最多 30 字；`note` 可选，最多 80 字。有子榜的游戏写 `{"boards": {"vigil": {"note": …, "score": […]}}}`，某个子榜没写就用最外层的。读不到、格式不对：分数直接按千分位写，不报错。
- **复合编码的分数**：一条规则可以写 `fields` 把分数拆成几个数：`{"fields": {"d": [1e10, null], "s": [1e4, 1e6], "k": [1, 1e4]}, "fmt": {"s": "mmss"}, "text": "危险{d} · {s} · 斩 {k}"}`。
  每个字段 = ⌊(分数 − `from`) ÷ 除数⌋ mod 取模（取模写 `null` 就不取模），除数、取模都要是正整数；字段名 1–8 个小写字母（不能叫 `n`），最多 6 个；`fmt` 可选，`"mmss"` 把字段写成"分:秒"。
- **各游戏总榜**：`games.ts` 里登记的固定榜（`boards` 可写成 `{"id", "name"}`）在排行页"各游戏总榜"一组里各有一个标签，只写 id 的标签按"<游戏名>·<id>"兜底。

### 15.13 好友页

好友页"我的好友码"下面是一个大按钮：有系统分享（`navigator.share`）就叫"分享给朋友"（旁边留"复制链接"），没有（多半是电脑）就叫"复制我的好友链接"。用户自己关掉分享面板不算失败，别的原因分享不了就退回复制。
好友列表里点名字进对方的战绩页。请求次数和写入不变（15.4、7.2）。

### 15.14 好友在线

好友页能看到好友在不在线、在哪（"在掼蛋房里 · 3/4 人""在大厅"）。只给好友看；本人能在"我的"里关掉，关了谁都看不到（`docs/social.md` 1.2）。

| 接口 | 谁能调 | 请求 | 成功 | 错误 | 写入 |
|---|---|---|---|---|---|
| `POST /api/presence` | 登录；平台页和游戏页（kit 的 `arcade-kit/social`） | `{"place": "lobby" \| "game" \| "room", "game"?: 游戏 id, "room"?: 房间码, "seats"?: "3/4"}` | 204 | 400（`game` 不是登记的游戏、`room` 不是 6 位数字、`seats` 不是"数/数"）；401；403 | 见 7.2 |
| `GET /api/friends` | 不变 | — | 每个好友多 `"online": boolean`，在线又开着开关时还有 `"where": {place, game?, gameName?, room?, seats?}`；在线的排前面 | — | 0 |

- **节流**：位置没变（`place`、`game`、`room` 都一样，只是 `seats` 变了不算）时按 `presenceEveryMs`（110 秒）节流：不到这么久的直接 204、写 0 行；位置变了（进房、换游戏、回大厅）马上写，但同一个人最快 `presenceMoveGapMs`（10 秒）写一次。
  "变没变"和写在同一条 `UPDATE … WHERE` 里比，不先读。页面在前台每 2 分钟报一次、切回前台时补报一次，后台不报。
- **在不在线**：最近 `presenceOnlineMs`（5 分钟）内报过就是在线。**隐私开关** `users.show_where`（默认开）：关了以后好友那边 `online` 恒为 `false`、没有 `where`；报位置照常写。
- **存什么**：只在 `users` 上加三列（`presence_json`、`presence_at`、`show_where`），不建新表；`last_seen_at` 跟着一起写。
- **静默**：这个接口不该打扰玩家，"在线"类预算用完或全站只读时回 204 不写。

### 15.17 好友动态

好友的名场面按模板生成一条动态，只给好友看，保留 7 天；好友能点赞或扔一个道具，每条每人一次。本人能在"我的"里关掉（`showFeed`）。写在"在线"类预算：类别预算用完、全站只读、本人关了开关，就不生成，**结回照常**。

**两个来源**：
1. **实盘结回自动生成**（游戏不用改）：`settle` 成功、带了合格的 `stats` 时，平台判断要不要生成：只记"值得说"的——这一份净赢 ≥ 半份，或这一份里拿到了**第一次拿到**的称号；输了、`statsIgnored`、重复的 `op`、到期退回、放弃都不生成。
   存 `{tier, units, titles}`（`units` 是净赢按份算乘 10 取整）；文字在浏览器里拼，称号名读游戏的 `titles.json`。
2. **游戏报的娱乐名场面**：

| 接口 | 谁能调 | 请求 | 成功 | 错误 | 写入 |
|---|---|---|---|---|---|
| `POST /api/feed` | 登录；游戏页（kit 的 `postMoment`） | `{"game": 登记的游戏 id, "moment": 名场面编号, "n"?: [整数, …]}` | 204（超了每天 10 条、关了开关、预算用完都静默 204、不写） | 400（游戏没登记、编号不是 1–24 位 `[a-z0-9_]` 字母开头、`n` 超过 3 个或不是安全整数）；401；403 | 2；被丢的 0 |

   只报编号和数字，**文字由游戏的 `public/moments.json` 给模板**（`{"four_bombs": {"text": "{name}一副牌扔了 {n} 个炸弹"}}`）：只认占位符 `{name}`（发的人的昵称）、`{n}` `{n2}` `{n3}`，模板 ≤ 40 字，有别的花括号、缺数字、读不到、没有这个编号，那条就不显示；拼出来一律按纯文本渲染。
   每人每天（北京时间）10 条，两个来源合计；第 11 条起静默丢弃。

| 接口 | 谁能调 | 请求 | 成功 | 错误 | 写入 |
|---|---|---|---|---|---|
| `GET /api/feed` | 登录；平台页 | — | 200 `{"items": [{"id", "user": 公开资料, "game", "kind": "settle" \| "moment", "at", "data", "reactions": {"like": 3, "tomato": 1}, "mine"?: "like"}]}`：我和好友最近 7 天的，新的在前，最多 50 条；关了开关的人的不给 | 401 | 0 |
| `POST /api/feed/<id>/react` | 登录；平台页 | `{"kind": "like" \| 道具 id}`（道具 id 用 table-fun 的那几个） | 204；每条每人一次，再点不改、0 行 | 400；404（不是好友的、自己的、过期的、不存在的，一律 404）；429（每人每天 100 次） | 1；被拒 0 |

**存储**：`feed`（`id` 是时间前缀 + 随机，按 id 排序就是按时间；`data` JSON ≤ 200 字节；索引 `(user_id, created_at)`）和 `feed_reactions`；Cron 删 7 天前的（`id` 带时间前缀，赞按 `item_id` 范围删）；注销时删本人发的、本人赞的。
界面：动态页 `/feed`（全部，先 10 条、"加载更多"每次 10 条，称号的说明默认两行、长的能展开）；顶栏一个"动态"按钮，有新的带红点，点开是最新 8 条（电脑上挂在按钮下面，手机上从底下弹出半屏），底下"看全部"进动态页；好友页好友列表上方一行入口"好友动态 · N 条新"。"看过"记在本机 `localStorage` 的 `arcade.feedSeen`，只是提醒，换设备不同步。

### 15.18 异步挑战

把一局的开局（种子和设置）做成链接发出去，打开的人就是同一个开局；大家的成绩挂在同一个挑战下互相看得到。靠游戏规则核心的确定性，平台不重算、不解析，只存、只排序。只给登录的人；发给谁不限（不一定是好友）。

| 接口 | 谁能调 | 请求 | 成功 | 错误 | 写入 |
|---|---|---|---|---|---|
| `POST /api/challenges` | 登录；游戏页 | `{"game": 登记的游戏 id, "payload": 任意 JSON, "score": 安全整数, "stats"?: 任意 JSON}` | 200 `{"id", "until"}`；发起人这局的成绩同时记成第一条结果 | 400；413 `too_big`（`payload` 或 `stats` 超过 1 KB）；429（每人每天发起 20 个）；503（停增长档） | 4；被拒 0 |
| `GET /api/challenges/<id>` | 登录；游戏页 | — | 200 `{"game", "payload", "owner": {"userId", "displayName"}, "until", "results": [{"rank", "userId", "displayName", "score", "stats", "isMe"}]（前 50）, "count", "me": {"rank", "score", "stats"} \| null}` | 404 `not_found`（不存在、过期、格式不对一律这个）；401 | 0 |
| `POST /api/challenges/<id>/results` | 登录；游戏页 | `{"score": 安全整数, "stats"?: 任意 JSON}` | 200 `{"result": "ok"}` 或 `{"result": "already", "mine": {"score", "stats"}}`（交过了，回原来那条，不改） | 404；409 `full`（已有 100 个人交了）；400；413；503（停增长档） | 1；交过、被拒 0 |

- **每人每挑战只记第一次**：结果表主键 `(挑战 id, 用户 id)`，`INSERT … ON CONFLICT DO NOTHING`。**排序**：分数高的在前，同分先交的在前；越低越好的游戏交相反数。结果列表里是昵称和 userId，不给用户名。
- **数字**（`config.ts`）：有效期 30 天，过期后打开、交成绩都是 404；每人每天发起 20 个；每个挑战最多 100 个人交；`payload`、`stats` 各 ≤ 1 KB，原样存、原样回，平台不解析。
- **存储**：`challenges`（`id` 是 36 进制毫秒时间补到 9 位 + 64 位随机；索引 `(owner_id, created_at)` 给注销）和 `challenge_results`。Cron 按 id 范围删 30 天前的挑战和结果；注销删本人发起的挑战（连同结果）和本人交的结果。
- 记"排行榜"类预算；停增长档时发起和交成绩都 503，打开照常。单独部署（没有平台）时游戏不显示"挑战好友"。kit 先不包，开盘直接调；多个游戏用时再抽进 `arcade-kit/social`。

### 15.19 搭子战绩

好友房打完一场，游戏的房间服务端把同桌真人报给平台；平台按"我和他"两人一对累计：一起打了几场、各自赢了几场、做搭档几场、搭档时赢了几场。好友页每个好友下面写"一起打了 23 场 · 你赢 12 · TA 赢 9"，战绩页按游戏分开写在"和我一起"一栏。只给好友看，本人能在"我的"里关掉（`showMates`）。

**为什么不挂在 `settle` 上**：结回只有实盘才有，好友房的娱乐局不结回；而且一场里每个人各结一次，平台要把几次结回拼成一桌才知道谁和谁一起。所以单开一个方法，一场一次、整桌一起报。
**只走服务绑定**：钱包服务绑定（`WALLET`）上多一个方法 `together`，只有房间的服务端能调，浏览器碰不到（`/api` 里没有这条路）。

| 方法 | 参数 | 回话 | 写入 |
|---|---|---|---|
| `together(req)` | `{"op": 这一场的编号, "players": [{"userId", "team"?: 0–3, "win": boolean}]}`；`op` 8–64 位 `[A-Za-z0-9_-]`；`players` 2–8 个真人，`userId` 不重复；电脑不报；`team` 有队伍的游戏才带；`win` 由游戏定（掼蛋：这一场赢了的那队；德州：这个人离桌或散桌时净赢为正；麻将：这一场分数为正） | `{"ok": true, "pairs": n}`；`{"ok": false, "error": "bad_request" \| "bad_game" \| "busy" \| "internal"}` | 新的一对 2 行，已有的一对 1 行；只记已经是好友的对；重复的 `op`、不是好友的对 0 行 |

- `game` 取绑定上写的游戏（不信请求里的）。**只记好友**：先一条查询找出两两之间是好友的对，只给这些对写行（陌生人同桌不记；以后才加好友的从加好友以后算）。
  **一场只算一次**：每对的行上记着最后一次的 `op`，同一个 `op` 再报，`UPSERT … WHERE last_op <> excluded.last_op` 不加、0 行；游戏的 `op` 用房间编号 + 场次。
- 记"排行榜"类预算；不是正常档或预算用完都回 `busy`、0 行，游戏不重试、不提示玩家。和结回一样信游戏报的输赢（服务端说了算）；单机对电脑不报。kit 的 `reportTogether` 由房间在一场结束时调；单独部署没有 `WALLET` 绑定时直接跳过。

**看**：`GET /api/friends` 每个好友多一个可选的 `together: {"n", "wins", "theirWins", "teamN", "teamWins"}`（各游戏加起来）；没一起打过、或任意一方关了开关就不带。好友页按 `teamWins` 挑"最佳搭档"（`teamN` ≥ 3 里 `teamWins` 最多的）。
`GET /api/stats/<id>` 在 `relation` 是 `friends`、两边都开着、一起打过时多 `together: {"<game>": {同上五项}}`。
**开关**：`PATCH /api/me {"showMates": boolean}`；关了照样记（对方那边也要算），只是两边都看不到这一对。
**存储**：`mates`，`(lo, hi, game)` 主键（两人的 userId 按字典序），一对一行；删好友、屏蔽时删这一对的所有行（计进那两个接口的写入行数）；注销删 `lo` 或 `hi` 是本人的；不进 Cron。

### 15.20 邀请码

测好后关掉公开注册，之后**新人只能凭老用户给的邀请码注册**。管理员开关（5.8 的 `registration`）不变：开着时码可填可不填，关着时必须带有效的码。

- **码**：12 位 Crockford base32（60 bit），显示成 `ABCD-EFGH-JKMN`；不分大小写，输入时去掉空格和横线，`I`/`L` 当 `1`、`O` 当 `0`。一码一用。
  **存明文**：码本身是唯一索引，注册时直接按码查；很多人先生成、过几天才发，"我的"里没用的码要能再复制、再分享，只存哈希就只能撤回重生成。码只能拿来注册、7 天过期，泄露的代价很小，和"密码、恢复码、令牌只存哈希"不冲突。
  用掉、撤回、过期以后接口里只给末 4 位。链接 `/i/<码>` 打开注册页并预填好码（注册关着时也露出"注册"页签）。
- **额度**（管理员可调，存在 `settings` 的 `invite_rules`，即时生效）：`userQuota` 普通用户每人几个（默认 3，范围 0–100）、`adminQuota` 管理员每人几个（50，0–1000）、`ttlDays` 码的有效期（7 天，1–90）、`perDay` 每人每 24 小时最多生成几个（5，1–100）。
  "用掉的额度" = 已用的码 + 还有效的码（没用、没撤回、没过期）；过期、撤回的未用码把额度还回来；管理员能给某个人单独改（`users.invite_quota`，空 = 按角色用默认）；已用的码一直算在额度里，被邀请的人注销了也算。

| 接口 | 谁能调 | 请求 | 成功 | 错误 | 写入 |
|---|---|---|---|---|---|
| `GET /api/invite-codes` | 登录 | — | 200 `{"quota", "taken", "left", "todayLeft", "ttlDays", "codes": [{"id", "hint", "code"?, "createdAt", "expiresAt", "status": "unused" \| "used" \| "expired" \| "revoked", "usedAt"?, "usedBy"?: 公开资料 \| null}]}`，新的在前，最多 50 条；`code` 只有没用的才给；`usedBy` 为 `null` 表示用的人已注销 | 401 | 0 |
| `POST /api/invite-codes` | 登录；要 CSRF | `{}` | 201 `{"id", "code", "link": "/i/<码>", "expiresAt", "left"}` | 409 `quota_full`（带 `quota`）；429（24 小时满 `perDay`）；403；503（停增长档） | 3；被拒 0 |
| `POST /api/invite-codes/<id>/revoke` | 登录；要 CSRF | `{}` | 204 | 404（不是自己的、不存在、已用、已撤回） | 1；被拒 0 |
| `POST /api/auth/register` | 匿名 | 多一个可选 `inviteCode` | 同 15.2 | 403 `registration_closed`；400 `invite_invalid`；409 `invite_used`；429 | 带码 13；码不对 1 |

- **生成**：额度和每天的上限都写在插入语句的条件里（`INSERT … SELECT … WHERE (用掉的额度) < 额度 AND (24 小时内生成的) < perDay`），并发冲不破，被拒 0 行；不另开计数行。
- **注册时的顺序**：令牌桶 → 读开关（关着又没带码 403）→ 校验请求体（422）→ **试码**：`inv:ip:<ip>` 每 IP 每小时 10 次（成败都算，超了 429、0 行）→ 按码查（不对 400）→ `reg:ip`、`reg:all` → 用户名查重 → 一个 batch：
  ① `UPDATE invite_codes SET used_by = 新 id, used_at = now WHERE id = ? AND used_at IS NULL AND revoked_at IS NULL AND expires_at > now`；② users 那条改成 `INSERT … SELECT … WHERE EXISTS (SELECT 1 FROM invite_codes WHERE id = ? AND used_by = 新 id)`，
  credentials、sessions 以"users 里有这个新 id"为条件，第 ① 条没改成（并发里被别人先用了）后面一行都不写，回 409 `invite_used`；③ 与邀请人的好友关系一行（`accepted`），邀请人好友满了 200 就只是不加好友，号照建。D1 的 batch 是一个事务、按顺序执行。
- **试码的防撞库**：码 60 bit，每 IP 每小时 10 次。**不设全站每小时上限**：全站计数只要算了乱试的，就能被几个 IP 段耗光，挡住所有拿着真码的人；真码注册成功以后照旧受 `reg:ip`、`reg:all` 管。
- **删干净**：注销、一年清理删本人生成的所有码；本人用过的那个码 `used_by` 清成空（`used_at` 留着，邀请人那边还算已用）。Cron：没用的码过期或撤回满 30 天就删。隐私说明写明谁邀请了谁（邀请人能在"我的"里看到用了自己码的人的昵称）。
- **界面**：`/me` 的"邀请朋友"栏（还能邀请几个、生成、列表、复制链接、系统分享、撤回）；注册页的"邀请码"输入框（注册关着时必填）；管理后台一页：四个数、给某人改额度、全站的码和撤回。
- 管理接口见 15.7。存储：`invite_codes` 表（避开好友房邀请的 `invites`）和 `users.invite_quota`。

## 16. 监控和告警

不引入新服务、不给 Cloudflare 加新凭证：平台自己巡检、把结果放在公开的 `/api/monitor`；GitHub Actions 定时读它，用 `GITHUB_TOKEN` 开、关 issue。
仓库和接口都公开，所以接口返回、issue、日志里只有模块、检查项和计数，没有域名、IP、用户名、userId。

### 16.1 接口

| 接口 | 认证 | 返回 | 写 |
|---|---|---|---|
| `GET /api/health` | 无，任何档位都答 | `{"ok", "version", "db"}`：`db` 是 `SELECT 1` 成不成；查不了回 503 | 0 |
| `POST /api/client-error` | 无；只查 Origin，不要 `X-Arcade`（kit 的 `reportErrors` 用 `sendBeacon` 发，带不了自定义头） | 204；`game` 不在 `games.ts`、没有 `msg` 400；每 IP 每分钟超 10 条 429 | 见 7.2 |
| `GET /api/monitor` | 无，任何档位都答，`cache-control: no-store` | `{"checks": [{"id", "ok", "n"?, "pct"?, "skip"?}], "at"}`，`at` 是巡检最后一次写状态的时间 | 0 |

`/api/client-error` 的请求体 `{"game", "ver", "msg", "stack"?, "path"?}`：`msg` 截到 200 字、`stack` 截到 1,000 字、`path` 去掉 `?` 和 `#` 以后的部分（里面可能有房间码、邀请码），
整条 `console.error` 成一行 JSON 进 Workers Logs（`wrangler.jsonc` 的 `observability` 开着）。库里只存签名（游戏 + `msg` 前 80 字的 SHA-256 前 16 位）和计数，不存报错原文。
同一签名每个 isolate 5 分钟只记一次，刷屏的报错不会把监控类预算用光。

### 16.2 检查项和阈值

巡检是第 2 个 Cron（`*/5 * * * *`），每天 19:17 那次清理之后也跑一遍。阈值在 `config.ts` 的 `monitor*`。

| 检查项 | 失败的条件 | 说明 |
|---|---|---|
| `health:<游戏>` | 同域查 `/games/<id>/health`：5 秒超时、网络错、非 2xx、`ok` 不是 `true` | 只查 `status: 'playable'` 的游戏；回 404 算还没接（`skip: true`），不告警。没设 `SITE_ORIGIN`（本地、一键部署）不查 |
| `errors:<游戏>` | 10 分钟内浏览器报错 ≥ 20 条，或当前版本才出现、以前几天没见过的签名报到 ≥ 5 次 | 10 分钟的数按状态里的快照算：快照只在当天总数变了时记，10 分钟前或更早里最新的那条就是 10 分钟前的数 |
| `wallet` | 有钱包的余额或桌上的筹码不是非负整数 | 每天那次查，其余几次沿用。各天的筹码统计记不下已结的带入，算不出逐笔对账，所以只查这个 |
| `quota` | 当天用量（调用数、写入、读取里最高的那项）≥ 停服线（6.6 的 `off`）的 80% | 读 `/api/monitor` 时按计量现算，不存 |
| `cron` | 状态 30 分钟没更新 | 状态没变时每 15 分钟也写一次心跳，加上 Cron 的 5 分钟间隔，正常时最多 20 分钟旧，漏掉一次 Cron 也不报 |

状态放 `settings` 的 `monitor` 一行 JSON，只在结果变了时写（另加每 15 分钟一次心跳，每天约 96 行），写入记在监控类（7.2）。停服档不巡检。

### 16.3 告警流程

- `.github/workflows/monitor.yml`（维护者的流程）每 10 分钟读一次 `/api/monitor`，主机名在仓库 secret `MONITOR_HOST`。
- 某项转为失败：开 issue（标签 `alert`，标题"告警：<检查项>"）；同名的已开着，只追评论，每小时最多一次。恢复：评论并关闭。
- 演练：在 Actions 里手动运行 Monitor，`selftest` 选 `open` 会开一条「告警：selftest」，再选 `close` 关掉；走的是和真告警同一段代码，用来确认告警链路（issue、指派、手机推送）通着，不碰线上。
- 查问题：Workers Logs 里按 `client-error` 和签名找原文，接口的错误日志只有路径和错误类型。
